# Decisions

Each entry is one line. Newer decisions go at the bottom. See [PLAN.md](./PLAN.md) for context.

## Tooling

- **pnpm workspaces, not Nx.** There are six packages with a simple dependency graph, and the Angular CLI already builds the web app; Nx would add config and a daemon without paying for itself.
- **Workspace packages export TS source** (`exports: ./src/index.ts`). Wrangler (esbuild), Vite/Vitest and the Angular builder all compile TS, so there is no build or watch step for libraries.
- **TypeScript ~6.0.3, not 7.x.** Angular 22 and typescript-eslint both require `<6.1`.
- **Vitest 4.1.x everywhere.** `@cloudflare/vitest-pool-workers@0.22` requires `^4.1`, and one version avoids duplicate installs.
- **Node ≥ 22.22.3 (24 recommended).** Angular 22's CLI refuses older versions (`.nvmrc` = 24).
- **ESLint 10 flat config with `typescript-eslint` strict (non-type-checked).** It is fast and catches `any`. Angular templates are type-checked by `strictTemplates` rather than linted.
- **Worker `compatibility_date` 2026-08-15.** This is the newest date supported by the workerd bundled with vitest-pool-workers 0.22. Bump it when the pool updates.

## Backend

- **Hono.** It is small, Web-standard, has first-class Workers support and also runs on Node, which keeps a port cheap.
- **Drizzle over Kysely for D1.** It has an official D1 driver with `batch`, drizzle-kit generates the Wrangler migrations, and `kysely-d1` has had no release since April 2025. Recursive CTEs use Drizzle's `sql`.
- **Recursive CTE for ancestor lookups.** It is O(depth) primary-key hops and needs no write-time bookkeeping. Subtree queries only occur in share/export, which load the whole tree anyway.
- **Branches are first-class rows, and each branch is a linear chain.** The outline is a tree of branches with a title, mode and count. Mode, anchor, privacy and model all attach to the branch.
- **`UNIQUE(branch_id, seq)`** lets the database reject racing appends to the same branch, even outside the DO.
- **One Durable Object per tree (`TreeSession`) owns generations.** `waitUntil`'s 30 s cap can't finish long streams after a disconnect. The DO also enables reconnect-with-replay and serializes sends per tree.
- **The DO keeps event buffers in memory only.** Final content goes to D1 once, and a restarted DO marks orphaned `streaming` nodes as interrupted. That is simpler and cheaper than persisting every delta.
- **SSE over `fetch()` streaming in the client**, because send is a POST (EventSource only supports GET). Reconnect uses `GET /api/nodes/:id/stream`.
- **Summaries are cached in D1**, keyed by `(anchorNodeId, sha256(transcript+focus), model)`. A changed transcript means a changed hash, so invalidation is implicit and lazy.
- **Summary provider/model are configured by `SUMMARY_PROVIDER_ID`/`SUMMARY_MODEL`**, defaulting to the branch's own provider/model. A cheaper model (e.g. `claude-haiku-4-5`) is recommended in the README.
- **`chars/3.5` token estimate plus the provider's reported usage.** There is no tokenizer to ship. The inspector uses Anthropic `count_tokens` when the provider supports it.
- **Share snapshots are stored in D1 as 256K-char chunks, not R2.** This keeps one storage system and makes republish atomic in a single batch. Chunking stays under the 2 MB row and 100 KB statement limits because values are bound, not inlined.

## Providers

- **Raw `fetch` + our own SSE parser instead of vendor SDKs.** This means zero dependencies, it works on any Web runtime, gives uniform abort handling, and handles the OpenRouter quirks explicitly.
- **AI Gateway is optional, via `baseUrl` + `extraHeaderSecrets`.** It adds logging and retries, but its cache does not apply to streams, so it isn't required.
- **Provider instances come from the `PROVIDERS` JSON var**, falling back to built-in defaults (anthropic, openai, openrouter; `fake` was one until _Fake reply removed_). API keys come from Worker secrets named in each config.
- **The default model is `claude-opus-5-5`.** No `temperature` and no assistant prefill are ever sent, because Opus/Sonnet 5.5 reject them.

## Context

- **`path` mode is compositional:** it inherits the parent's effective context at the branch point. A path branch under a summary or independent branch therefore doesn't re-expand what that ancestor dropped.
- **The anchor quote is included in every mode**, placed before the branch's own messages. It also focuses the summary in `summary` mode.
- **`message` mode sends only the branch-point message**, between `summary` and `independent`: the quote alone often lacks the surrounding answer, but the whole path is more than the branch needs. It is the node as the parent saw it (no summary call, no earlier turns, no inherited system nodes), and it is skipped like any path node when it is an in-flight or failed reply.
- **The tree system prompt is sent in every mode, including `independent`.** It is configuration, not conversation.
- **Summaries are rendered into the system prompt**, not as fake messages, so user/assistant alternation is never broken. (Anchors were too, until the prompt caching audit made them quoted user text.)
- **Compaction replaces the oldest prefix of the context with one cached summary.** Truncation is only a last resort, and both are recorded in the plan.
- **Compaction goes down to about half the budget, in whole steps, so later turns reuse it.** Compacting only what a turn needed made every later turn over the cap compact one more segment: a new summary call and a new prompt prefix on each turn, so every turn missed the prompt cache exactly when the context was largest (in a test conversation, 16 summary calls in 16 turns). The compacted prefix now holds the overflow rounded up to whole steps of half the budget (`AssembleBudget.compactionTarget`, `DEFAULT_COMPACTION_TARGET` 0.5), plus the summary's estimate. That is a function of the context alone, with no state: the boundary, and so the summary's key and the prompt after it, stays the same until the context outgrows the budget by another half, so the next turns find the summary in the cache and send the same prefix (3 summary calls in the same 16 turns). The cost is less verbatim history right after a compaction. When the protected tail is too large for a whole step, all the candidates are compacted if that fits; the next turn then moves to the step boundary once.

## Sharing & access

- **The public viewer is a self-contained, server-rendered page, not the Angular app.** It needs no session, works on phones, uses a strict hash-based CSP, and is the _same function_ as the HTML export.
- **Shares live on `/s/*` of the app's own hostname rather than a separate one.** There is one domain to manage. The page is self-contained under a strict CSP, `/s/*` never reads the session, and session cookies are HttpOnly.
- **Revocation is checked on every request against D1, and cache keys include `version`.** Revoke and republish take effect instantly and globally without a global purge (the Cache API is per-colo).
- **Private exclusion happens in the pure projection.** Private branches never enter the payload, and creating a share of a private target is rejected.
- **Share keys (`b0`, `m3`) are per payload.** No internal ids leak to viewers.
- **Exports exclude private branches by default.** The owner can opt in with `includePrivate=true`. JSON backups always include everything.
- **The Worker fails closed if sign-in isn't configured.** `DEV_ALLOW_NO_AUTH=true` is honoured only while `BETTER_AUTH_SECRET` is unset, and belongs in `.dev.vars` only.
- **Markdown uses markdown-it (`html:false`) + highlight.js, shared by Angular and the Worker.** It needs no DOM, so there is one renderer and the output can't diverge. Angular's sanitizer is a second layer.

## Integration (post-merge)

- **Stale `streaming` nodes are recovered lazily**, when a fresh DO instance first serves a tree and when a client reconnects. No alarm is needed, because a restart always precedes the next access.
- **The Fake provider never auto-titles** (now only the test provider, see _Fake reply removed_): the title would just echo the prompt. Branches keep the readable default title, which is the anchor quote or the first words of the message.
- **Angular bundle budget warning set at 1.5 MB (≈235 kB gzipped).** zod, markdown-it and highlight.js ship with the shared packages; that is acceptable for a single-user app.
- **The Hono app lives in `apps/worker/src/app.ts` (`createApp`)**, so tests can inject a local JWKS. `index.ts` only exports the handler and the Durable Object.
- **Viewer tables use `ta-left/center/right` classes instead of inline `style`**, because the share page's strict hash-based CSP blocks inline styles.
- **A share whose fork node is filtered out** (a system, streaming or error node, or a node before a subtree target) drops that child branch and everything below it.

## Accounts (multi-user)

- **Trees and shares carry `account_id`.** It references an `accounts` table seeded with a single `default` account in migration 0001. Existing rows backfill via the column default, so there is no data rewrite.
- **Branches, nodes and summaries inherit ownership through `tree_id`.** They have no column of their own, so per-user data is a matter of filtering by tree.
- **One place decides the acting account:** `resolveAccount(env, identity, request)` in `apps/worker/src/auth/account.ts` (rewritten by _Open sign-up and the mode switch_ below).
  - Every signed-in user → `p_<userId>` in `power` mode, or `u_<userId>` in `simple` mode, whichever app the request comes from. The ids derive from the Better Auth user id (stable, unlike email), so resolving them needs no lookup and can't race.
  - The dev bypass → `default` (power) or `default_simple` (Learn).
- **Account rows are created on first use** (`INSERT OR IGNORE`, memoized per isolate) by `accountMiddleware`. Migration 0003 adds `accounts.user_id` and `accounts.mode`; migration 0005 makes `(user_id, mode)` the unique pair. The `default` row stays `power` with no user id.
- **`AppVariables.account` (`{ id, mode, userId }`) replaces the bare account id.** `accountId` stays as an alias. Routes need the mode for gating (BYOK, billing, rate limits, the default system prompt).
- **Sign-up is open to everyone with a verified email** (replaces "open sign-up is off by default"). `user.create.before` refuses unverified users and the session middleware re-checks on every request, because the email is what makes the accounts theirs.
- **Tree ownership is enforced in `ChatService`.** `getOwnedBranch`/`getOwnedNode` report another account's branch or node as 404, like a missing one. `createBranch`, `updateBranch`, context planning, `beginSend`, `prepareReview` and `deleteBranch` use them, and the Worker resolves every branch or node id through them before it talks to the Durable Object. One enforcement point, consistent with the tree-level checks.
- **The Durable Object trusts the account the Worker passes** (in the `/send` body, or as query parameters on its other internal routes). Those routes are internal; the Worker has already checked ownership.
- **Services take the account id.**
  - `listTrees`/`listShares` filter by it.
  - Tree-level operations (detail, update, delete, backup) and share management treat another account's rows as not found.
  - Imports are assigned to the importing account.
- **The user picks the mode** (replaces "allowlisted users always get power mode" and the redirects between the apps). See _Open sign-up and the mode switch_.
- **`account_id` has no FK constraint.** SQLite cannot `ALTER TABLE … ADD COLUMN` with `REFERENCES` and a non-null default.
- **Per-account settings live in their own table, `account_settings` (migration 0006), not in columns on `accounts`.** The first setting is a system prompt of up to 20k chars that is read only when a tree is created or Settings opens, while `accounts` is the small row every request ensures; a row is written only on the first save (an upsert), so "no row" means the defaults and nothing is backfilled. Typed columns rather than a key/value table, so Drizzle checks them; no FK, like every other `account_id`.
- **Settings are per account, not per user.** Power and Learn are separate accounts with separate conversations, so each keeps its own default prompt, and the settings ride on the existing account scoping (`ChatService.getSettings`/`updateSettings`, `GET`/`PATCH /api/settings`).

## Bring-your-own-key

- **User keys live only in the browser, as one AES-256-GCM-sealed HttpOnly cookie (`__Host-llmkey`).** Only the Worker has the secret (`KEY_ENCRYPTION_SECRET`). We rejected localStorage/IndexedDB, where XSS or a compromised dependency can read the key, and client-side passphrase or WebCrypto schemes, where XSS can simply call `decrypt()`.
- **One cookie holds a map of provider id → key**, not one cookie per provider. Branches pick their provider, and summaries or titles can run on another one, so every provider-calling request needs the whole set. One cookie also means one decrypt, atomic updates, and a single "forget".
- **The sealed format is `v1.` + base64url(iv ‖ ciphertext ‖ tag).** It uses a fresh 12-byte IV per seal and AAD `tangent/llmkey/v1`. The payload carries `exp`, which is enforced server-side as well as by `Max-Age`, and `uid`, the user it was sealed for: another user's cookie opens as no key, and sign-out clears it. Every failure to open it means "no key" (401 `key_required` plus clearing the cookie), never a 500.
- **User keys override server secrets per provider id** through `ProviderEnv.apiKeys`. A provider with no `apiKeySecret` becomes available once the user supplies a key.
- **The Durable Object receives the still-sealed cookie value in the internal request body** and opens it itself. The body is not logged, whereas headers may be. The plaintext key lives only in the ChatService for that generation.
- **Generations still outlive the tab.** This is the existing reconnect design, so closing the tab does not abort. The Stop button (`/cancel`) aborts the upstream request, which stops billing.
- **The proxy is the abuse boundary**, because XSS can still ride the cookie:
  - requests must be same-origin (a `same-site` subdomain is rejected too, which SameSite alone allows);
  - the model must be in the provider config;
  - `max_tokens` is server-set;
  - there are 30 generations/min per cookie, bucketed by the SHA-256 of the sealed value;
  - saving a key (which makes a verification call) is limited per account.
- **Key verification is `GET /v1/models` (Anthropic) or `GET {baseUrl}/models` (OpenAI-compatible).** Only 401/403 rejects a key; if the provider is unreachable, saving is not blocked. OpenRouter's `/models` is public, so there the check proves nothing.
- **The web app gets a strict CSP via Workers Static Assets `_headers`**: `script-src 'self'`, `connect-src 'self'`, `img-src 'self'`, Trusted Types (`angular`, `angular#bundler`). Critical-CSS inlining is off because it needs an inline script. zod runs `jitless`, because its `new Function` probe is reported as a violation.

## Deleting branches

- **Deleting a branch deletes its whole subtree.** Child branches hang off its messages, so they cannot outlive it. The trunk cannot be deleted; deleting the conversation covers that.
- **Summaries anchored on deleted messages and shares targeting them are deleted too** (in the same D1 batch). Whole-tree snapshot shares keep their frozen copy until republished or revoked.
- **Deletion goes through the tree's Durable Object.** It holds the send lock so no message lands in the doomed branches, aborts their running generations and waits for them to persist, then deletes. Without that hook (e.g. a Node port), `ChatService.deleteBranch` refuses with 409 while a reply is generating there.
- **Branch titles are editable inline in the outline** (double-click or the pencil) as well as in Branch settings; either marks the title `user` so auto-titling leaves it alone.

## Reviewer ("Review up to here")

- **A review is advice about the tree, not part of it.** It is streamed and never stored, so it can't leak into later context, shares or exports. It enters the conversation only if the user sends it, through "Add corrections to the message box". The web app keeps reviews in memory for the session.
- **The reviewer sees exactly what the reviewed model saw.** That is the branch's rendered context plan for that reply, with summaries resolved and cached as on a normal send, so a mistake caused by a lossy summary shows up as one. It is wrapped as a transcript in one user message, so the reviewer judges the replies instead of continuing the chat.
- **The verdict is a two-line trailer (`ACCURACY: OK|MINOR|MAJOR`, `RECOMMENDATION: STAY|UPGRADE`).** It is parsed leniently by `parseReview` in `@tangent/shared`, which also holds the labels that the prompt uses. We chose a text trailer over JSON/tool output so the prose streams readably on every provider. A missing trailer means no badge, never an error.
- **The client picks the reviewer's provider/model per request.** This is the one generation route where it does. The model allowlist, the server-set output cap, same-origin and the per-cookie rate limit still apply.
- **Reviews stream straight from the Worker, not through the tree's Durable Object.** There is no persisted run to reconnect to. A client disconnect aborts the upstream request.
- **The default reviewer is a browser setting (localStorage, `tangent.settings`).** It is not a secret, and every request names its model anyway. If it is unset or unusable, the branch's provider default is used. Server-side per-account settings can replace it when multi-user arrives. (They now exist, `account_settings`, but hold only the default system prompt so far; the reviewer stays in the browser.)

## Authentication (replaced Cloudflare Access)

- **Better Auth in the Worker instead of Cloudflare Access in front of it.** Sign-in is part of the app (Google, GitHub, magic link, passkeys), it works on any host, and the Worker stays the only security boundary. Its tables live in D1 as `auth_*` (Drizzle schema, migration 0002), so its `account` model can't be confused with our `accounts`.
- **No passwords.** Email+password stays disabled; the methods are OAuth, magic link and passkeys. Passkeys are added from the Account dialog once signed in.
- **Anyone may sign up** (replaces "`ALLOWED_EMAILS` gates sign-in, and everyone on it shares the default account"). Unverified users are never created (`user.create.before` returns false, so the OAuth callback redirects to `/login?error=unable_to_create_user` instead of answering JSON). Turnstile and the magic-link rate limits stay the abuse boundary for sign-up.
- **The API session check never refreshes the session.** A refresh must re-issue the cookie, which only `GET /api/auth/get-session` does; the web app calls it at startup. Refreshing in the middleware would move the database expiry while the cookie kept its old one.
- **"Remember me" for every method via an after-hook.** Better Auth only has it for email+password. Sessions start remembered (30 days, extended at most daily); when the login page's one-shot `tangent-remember` cookie isn't `1`, the hook shortens the row to 1 day and re-issues the cookie with no Max-Age plus Better Auth's signed `dont_remember` cookie. It's a cookie because the OAuth callback and magic link are top-level navigations. Missing (e.g. a link opened in another browser) means not remembered.
- **Captcha only on `/sign-in/magic-link`.** It is the one endpoint that sends email; OAuth providers run their own bot checks and passkeys can't be scripted. Without `TURNSTILE_SECRET_KEY` the plugin refuses the request (fails closed). Hostname pinning is skipped on localhost because Turnstile's test keys report their own hostname.
- **Turnstile only runs in the `/login` document, which has its own CSP.** `_headers` detaches the app-wide CSP for `/login` and allows `challenges.cloudflare.com` there, without Trusted Types (the page renders no model output). The app reaches `/login` and leaves it only by full page loads, so third-party script never runs in a document holding conversations or the key cookie's API access.
- **Better Auth's rate limiter stores counters in D1.** Memory storage would be per isolate. The client IP comes from `cf-connecting-ip`.
- **Email goes through an `EmailSender` interface** (`apps/worker/src/email/`), picked by `EMAIL_PROVIDER` in one function. Resend is called with raw `fetch` (no SDK), like the LLM providers. The `log` sender prints links to the console and is refused off localhost, since a logged magic link is a credential.
- **Magic-link tokens are stored hashed** and expire after 15 minutes.
- **`nodejs_compat` is on**, because Better Auth imports `node:async_hooks`.
- **`pnpm dev` passes `--local-upstream localhost:8787`.** Otherwise wrangler rewrites local requests to the production hostname from `routes`, and Better Auth's origin check rejects them.

## Simple mode and billing

> **Payments moved to Polar (2026-10).** The bullets here that name Stripe, Stripe Tax, the Better Auth Stripe plugin, `auth_subscriptions` or `stripe_ref` record the earlier design and are superseded by [Payments behind a port (Polar)](#payments-behind-a-port-polar) below. The rest still holds.

- **A separate simple app (`apps/simple`) rather than a mode of the power app.** The owner asked for one, and a lean `LessonStore` doesn't drag the inspector, reviewer, shares and BYOK along.
- **Shared Angular code lives in `packages/web-shared`, exported as TS source.** The same convention as the other packages: both apps' Angular builders compile it AOT through the pnpm symlinks, so there is no library build. `TreeStore` and the power dialogs stay in `apps/web`.
- **The simple app is served at `/learn/` on the same origin and Worker.** Better Auth cookies, passkeys (rpID = host), OAuth callbacks, Turnstile's hostname, `PUBLIC_BASE_URL` and the CSP all stay single-origin; a second hostname would duplicate every one of them.
- **The Worker serves `/learn*` and sets its CSP itself** (`http/learn-app.ts`). SPA fallback only ever serves the root `index.html`, and `_headers` isn't applied to Worker-generated responses. A test keeps the Worker's copies identical to the `_headers` policies.
- **Both builds are assembled into `apps/worker/site/`** (`scripts/assemble-assets.mjs`, plain Node fs), not under `dist/`, so git can keep a `.gitkeep` that lets wrangler and the tests start before anything is built.
- **One server-side provider, `tangent` (OpenRouter; since _Funding apart from the provider_ its id is the endpoint `openrouter`), is the only provider in a simple account's registry.** The generic provider checks then apply unchanged. Two tiers: Smart (`deepseek/deepseek-v4-pro`) and Simple (`deepseek/deepseek-v4-flash`), both configurable; `SIMPLE_PROVIDER` replaces the whole config (tests, AI Gateway, `options.extraBody`).
- **A dedicated `OPENROUTER_SIMPLE_API_KEY`, with no fallback to `OPENROUTER_API_KEY`.** Customer spend stays separate from the owner's, and the key can carry a hard credit limit as a backstop.
- **Simple accounts get the built-in prompt (see "One default prompt for both modes" below), capped input (`SIMPLE_MAX_INPUT_TOKENS`, 60k) and output (4,096, or 16,384 on a reasoning model, whose hidden thinking counts as output; see below), and summaries and titles on the fast model.** The pedagogy is server-controlled, and the caps bound the cost of any one call.
- **The Learn prompt answers first and suggests tangents; it is not Socratic.** The first prompt guided with questions and hints before answers. That is slow, and it fights the product: the tree already lets the learner drill into whatever they don't follow, so the tutor's job is the best possible answer to the question actually asked, plus 2–4 places to go next. Those come in a fixed `<tangents>` block (parsed by `splitTangents` in `@tangent/shared`, rendered as branch buttons in Learn); a tapped tangent becomes a `path` branch titled after it, with the title as the first message, so the model answers it in context. The block stays in the stored reply (and in later context) so the model knows what it already offered; a half-streamed block is never rendered as text.
- **Learn on paid credit ignores the user's keys and is rate limited per account** (per user across both apps since _Unified billing and model access_). It spends the operator's key, so the account is the abuse boundary. Learn on the user's own key is BYOK like power mode (see below).
- **Metering wraps the `ProviderRegistry`** (`billing/meter.ts`). Every provider call (replies, summaries, titles, reviews) goes through it, so nothing in `ChatService` changes beyond a `usageTag` on each request. Only Learn on paid credit is metered (`isMetered`; now per call on the built-in provider, see _Unified billing and model access_).
- **A pending `usage_events` row is written, and awaited, before every upstream call.** No row, no call; a crash can leave a row pending but never double-charge, because every settle is one conditional `UPDATE … WHERE status = 'pending'`.
- **Cost starts from OpenRouter's reported `usage.cost`, never a price table.** Prices drift (and differ per upstream), and the reported cost is what we pay per call (before OpenRouter's credit-purchase fee; see the true-cost decision below). The generation id (`X-Generation-Id`, or a chunk `id`) is stored as soon as it is known. (Since the community pool, there is a price table too, in `src/config.ts`: it bounds pool reservations, caps OpenRouter's routing price for pool calls and settles pool calls that report no cost. A reported cost still wins; see _Community credit pool_.)
- **A stream that ends without a cost is reconciled via `GET /api/v1/generation`** with retries at 1, 3, 10 and 30 s, since the endpoint 404s for a few seconds. Aborted streams never get the final usage chunk.
- **A cron every 10 minutes is the backstop.** It covers Durable Object eviction mid-stream: rows with a generation id settle from OpenRouter; rows without one after 10 minutes never reached OpenRouter and settle at $0.
- **Rows still unresolved after 24 hours become `unresolved` at $0 and are logged.** A bounded loss, for manual review, rather than holding the user's balance forever.
- **The ledger is integer micro-USD; provider cost is stored in nano-USD.** `charge = ceil(costNanos × (10000 + feeBps) × (10000 + markupBps) / 10¹¹)` in exact integer (BigInt) math: never rounded down, and the bias is under $0.000001 per call.
- **The balance is computed, not cached:** `Σ credit_grants − Σ settled charges`, minus pending holds for "available". Every write is one idempotent statement, so there is no cross-table atomicity to get wrong.
- **Markup is applied when usage settles, at the rate fixed when the call started:** `MARKUP_MONTHLY_BPS` (+5%) with an active subscription, else `MARKUP_PREPAID_BPS` (+10%), on the true cost (below). It is the owner's literal rule, one formula, and keeps the balance in plain pre-tax dollars. Credit bought at one rate may be spent at the other. (Since _Unified billing and model access_, one rate: `MARKUP_BPS`.)
- **Sends need `available ≥ USAGE_HOLD_MICROS` ($0.02), else 402 `payment_required`.** A running generation is never cut off; overdraft is bounded by the caps and the hold, and the next purchase absorbs a negative balance.
- **Prepaid credit uses our own Checkout Session (`mode: 'payment'`) with `price_data` on `STRIPE_CREDITS_PRODUCT_ID`.** The plugin can't do one-time payments, and inline prices keep the $5–$500 amount server-validated.
- **Monthly plans are recurring prepaid credit, through the Better Auth Stripe plugin.** Every paid subscription invoice with a positive subtotal credits that pre-tax subtotal less Stripe's fee, which rolls over, whatever its `billing_reason` (create, cycle, a prorated update, threshold): whoever paid an invoice gets its credit, even if the Customer Portal is set up to prorate. `prorationBehavior: 'none'`, so plan switches through the plugin apply next cycle. Plan changes, cancellation, cards and invoices are all in the Stripe Customer Portal. (Removed in _Unified billing and model access_: the plugin's one subscription is now the membership.)
- **Rejected: metered (postpaid) Stripe billing.** It would need reliable meter-event delivery with retries, a reconciliation job against Stripe and spend caps against unpaid invoices, plus credit risk. Prepaid tiers need none of that and share one ledger.
- **Stripe Tax, not Managed Payments.** The owner asked for Stripe Tax. Prices are tax-exclusive, `automatic_tax` is on in both Checkout flows, and only pre-tax amounts (`amount_subtotal`, `invoice.subtotal`) enter the ledger.
- **One webhook: the plugin's `/api/auth/stripe/webhook`, with our logic in `onEvent`.** One endpoint and one secret for the operator, and the plugin keeps its subscription table in sync. Throwing from `onEvent` makes the plugin answer 400, so Stripe retries.
- **Accepted quirk: the plugin calls `subscriptions.retrieve(null)` for payment-mode `checkout.session.completed`.** It fails, is logged, and `onEvent` still runs. One wasted API call and one log line per top-up; a test asserts the credit is still granted.
- **Grants are idempotent on the Stripe object id** (`credit_grants.stripe_ref` is unique: session, invoice or refund id), so redeliveries are no-ops. (Since the pool, also dispute ids, `<dispute id>:reinstated`, `admin:<key>` for admin adjustments and `dev:<key>` for simulated purchases. The spec asks for idempotency on the event id; the object id is strictly stronger: the same session arriving through both `checkout.session.completed` and `checkout.session.async_payment_succeeded`, two different events, still credits once.) Webhooks find the account by `metadata.accountId` (top-ups) or by `customer` → `auth_users.stripe_customer_id`, so grants don't depend on the plugin's row existing yet.
- **Refunds debit automatically (`charge.refunded`), one negative grant per refund.** For top-ups only the pre-tax share is debited; disputes are handled by hand with an `adjustment` grant. (Since the pool, disputes of top-ups and pool purchases are automatic: `charge.dispute.funds_withdrawn` debits like a refund of the disputed amount, keyed on the dispute id; `charge.dispute.funds_reinstated` credits back what was debited; a dispute closed as `lost` suspends the buyer's pool access. Disputes of membership invoices are still handled by hand.) The debit is the full pre-tax refund although the purchase was credited net of Stripe's fee: Stripe keeps its fee on a refund, so the refund passes that cost on rather than the operator absorbing it.
- **Stripe customers are created lazily** (`createCustomerOnSignUp: false`), on the first top-up or plan checkout, with the plugin's metadata keys and an idempotency key per user. No Stripe calls for the owner or for sign-ups that never pay.
- **`stripe@^22.6.2`, not 23.** `@better-auth/stripe@1.7.7` accepts `stripe` ^18–^22 only. 22.6.2 pins API version `2026-08-26.dahlia`; the webhook endpoint is created on the same version.
- **The plugin is registered only when both Stripe secrets are set,** but its `subscription` table is always mapped, so the schema doesn't depend on configuration. Without Stripe, paid credit isn't offered and Learn runs on the user's own key only.
- **"Cost" means the operator's true cost, so the markup is real margin (replaces R1, "the default markups likely lose money").** The owner's rule is cost + 10% (prepaid) or + 5% (monthly plan); charging only OpenRouter's reported price lost money on small purchases, and "if I'm losing money charging cost, it's not cost". Two fees are passed through, and the markups stay config (`MARKUP_*_BPS`):
  - **OpenRouter's credit-purchase fee grosses up each call's cost** (`OPENROUTER_FEE_BPS`, default 550 = 5.5%), multiplied in before the markup. It is a rate rather than a lookup because OpenRouter bills it when the operator buys credits, not per generation; operators who buy in amounts small enough to hit the $0.80 minimum set a higher rate.
  - **The fee rate is stored on each `usage_events` row (`fee_bps`), like `markup_bps`.** A settle, a deferred reconcile and the cron all use the row's stored rate, so changing the config never reprices calls already made; rows from before migration `0004_fees` keep 0.
  - **Purchases are credited net of Stripe's exact fee, read from the payment's balance transaction** (`PaymentIntent` with `expand: ['latest_charge.balance_transaction']`; for invoices, the paid `invoice_payments` first). An estimate (2.9% + 30¢) would be wrong for international cards, wallets, ACH and pricing changes; the balance transaction is what Stripe actually took, itemised in `fee_details`. Until it exists, fulfilment throws and Stripe redelivers.
  - **The fee is taken off the pre-tax subtotal, never the tax.** Stripe charges it on the tax-inclusive total, which is a real cost of the sale; tax itself is still never credited.
  - **Each grant records `gross_micros` (pre-tax paid) and `fee_micros`**, with `amount_micros` the net credit, so the billing page can say "paid $5.00, credit $4.52 after payment processing" and the ledger formula stays `Σ amount_micros`.

A reply's cap is `ChatSettings.reservedOutputTokens` (4,096) on a plain model and `reasoningOutputTokens` (16,384) on a reasoning one (`ProviderCapabilities.reasoning`: `ModelInfo.reasoning` in a provider config, else the `isReasoningModel` id heuristic in `@tangent/shared`), always within the model's `maxOutputTokens` (a reasoning model without a configured limit: 32,000). Summaries and titles get 4,096 instead of 1,024 on a reasoning model. A bigger cap costs nothing by itself: a call pays for what it generates. ## Community credit pool

> **Payments moved to Polar (2026-10).** The bullets here that name Stripe, Stripe Tax, the Better Auth Stripe plugin, `auth_subscriptions` or `stripe_ref` record the earlier design and are superseded by [Payments behind a port (Polar)](#payments-behind-a-port-polar) below. The rest still holds.
>
> **The pool is revenue-funded (2026-10-05).** Nobody buys pool credit any more, and pool replies carry no markup: the bullets here about pool purchases, their `target`, minimum, pricing and markup record the earlier design and are superseded by [Revenue-funded community pool](#revenue-funded-community-pool) below. Refunds and disputes of legacy pool purchase rows still work as described.

The pool is specified in `docs/pool/SPEC.md` and planned in `docs/pool/PLAN.md`; these are the decisions of its ledger, bank and settlement.

- **The pool is one more ledger account in the same two tables (`POOL_ACCOUNT_ID`, default `pool`), not a new ledger.** The spec's entry types map onto them: `purchase` and `admin_adjustment` are `credit_grants` rows (kinds `purchase`, `adjustment`); a `reservation` is a `usage_events` row inserted `pending` with `funding = 'pool'` and `hold_micros` = the call's worst case; a `settlement` is that row moving to `settled` with `charge_micros` and `settle_reason` (`cost`, `generation`, `tokens` or `hold`); a `refund_of_reservation` is the same transition with `settle_reason = 'released'` and a charge of 0, the released amount being `hold − charge` on the row. **Spec deviation D1, accepted:** settlement and release are row states, not separate rows. A row never changes once it leaves `pending`, so the table stays effectively append-only, exactly as for personal credit.
- **Amounts stay integer micro-USD (provider cost in nano-USD), not millicents.** 1 millicent = 10 micro-USD, so micro-USD is finer, and every existing balance, hold and charge already uses it.
- **A `PoolBank` Durable Object per pool serialises every operation that can lower the pool's available balance; D1 stays the authority.** `available = Σ grants − Σ settled charges − Σ pending holds` never goes below 0 because what lowers it (inserting a reservation; later, the debit of a refunded pool purchase) runs only under PoolBank's lock after checking the balance and the caps in one D1 batch. Settling, shrinking a hold, expiring and positive grants can only raise it, so they run anywhere without the lock. DO input gates don't hold across D1 I/O, hence the explicit promise-chain lock (the `sendLock` pattern of `TreeSession`).
- **PoolBank reads no pool config of its own.** Every cap, price, TTL and threshold arrives as an argument, resolved Worker-side from `appConfig(env)` (`pool/params.ts`), so a per-request env (and a test's) applies everywhere. The supporter tier is the exception that proves the rule: it is computed inside `reserve` from D1, never passed in.
- **A balance checkpoint keeps a reservation's sums to recent rows.** PoolBank stores `{balance, at}` = the sum of every row created before `at`; those rows never change once settled, so the sum never goes stale. The cron advances it to `min(now − 2 × give-up, 00:00 UTC today)`, only when no older reservation is still pending, and once a day compares it with a full ledger sum: a mismatch is logged and the checkpoint dropped (the ledger wins).
- **Pool charges are clamped to their hold; the excess is `overage_micros`, absorbed by the operator and bounded by a breaker.** A settle can then never lower `available`, so the invariant needs no lock on the settle path. When the pool's overage in the last `POOL_OVERAGE_WINDOW_MS` (24 h) exceeds `POOL_OVERAGE_MAX_MICROS` ($0.20), every reservation is refused as `unpriced` and `pool_breaker_tripped` is logged at error level: a price in the table is below what calls really cost. The sum is re-read at most once a minute.
- **Settlement depends on whether the request was dispatched (`pool/settle-policy.ts`, one function for the meter, the alarm and the cron).** The meter stamps `dispatched_at` (awaited) right before the upstream call. Never dispatched, or failed before it was sent (`ProviderError.upstream = 'not_sent'`), or refused with a non-2xx status (`'rejected'`): released at 0. Otherwise, in order: the reported cost, a generation lookup, tokens × the price table (both counts observed), else the full hold. **Spec deviation D2, accepted:** the spec releases the whole reservation on failure or timeout; once a request is upstream, the pool pays for what it may have cost, so the operator's worst case stays fixed.
- **Stale reservations expire through PoolBank's alarm, backstopped by the cron.** A reservation older than `POOL_RESERVATION_TTL_MS` (10 min) belongs to a crashed or evicted request: never dispatched → released; dispatched with a generation id → one lookup (5 s timeout), then the full hold once older than `POOL_GIVE_UP_MS` (1 h); dispatched without one → the full hold. Each pass settles at most `POOL_EXPIRE_BATCH` rows in parallel, takes no lock (a reservation never waits for it), puts rows that need no lookup first, and re-arms itself. Calls time out after `POOL_CALL_TIMEOUT_MS` (120 s), clamped to at most the TTL minus a minute, so the alarm never expires a live call. Personal reconciliation filters pool rows out in SQL, so a pool backlog can't starve it.
- **Holds are true worst cases from a per-model price table (`MODEL_PRICES` over the defaults in `src/config.ts`).** The bound on input tokens is the request's UTF-8 length plus framing: byte-level BPE tokenizers never emit more tokens than bytes, where the chars/3.5 estimate is not a bound. A request whose bound exceeds the price entry's `contextTokens` is refused before anything is reserved or sent (`PoolRequestTooLargeError`, a `context_length` error), never clamped, so a hold bounds its call's cost even when `contextTokens` is set below the model's real window. Output is the pool's cap (`POOL_MAX_OUTPUT_TOKENS`), which the meter also forces on the request. A model without a price can't be used by the pool. The default prices are placeholders the operator confirms before enabling the pool.
- **A daily cron syncs OpenRouter's list prices into the price table (`pool/model-prices.ts`, `model_prices` in D1).** `GET /api/v1/models` is public; its USD-per-token decimal strings become µ$/MTok by exact decimal shifting (floats misround values like `0.0000002`), rounded up past the 12th decimal. Precedence: an explicit `MODEL_PRICES` entry, then the synced price, then the built-in placeholder. Only models with a configured entry are priced, so the sync refreshes a price but never makes a new model usable; the context window is the lower of the configured and listed one (a smaller window only refuses more and keeps the ceiling hold small). Increases apply whatever their size: holds grow, so the pool refuses earlier rather than overspending. A drop to under a tenth of the stored price is held back and logged (`price_sync_anomaly`): a bogus low price would shrink holds below real costs and trip the overage breaker. A failed fetch or a delisted model keeps the stored price. Every new or changed price is kept in `model_price_history`, and an override below the list price is logged (`price_override_below_list`). Before this, a price increase showed up only as the overage breaker closing the pool. The sync also stores the listed prompt-cache prices (`input_cache_read`, `input_cache_write`; migration `0024_model_cache_prices`) with the same precedence: a listed cache price replaces the placeholder's, an explicit `MODEL_PRICES` entry wins wholesale, and an unlisted one falls back (a read to the input price, a write to 1.25× the input on explicit-cache models, else the input price). A cache price's drop to under a tenth is held back like the others, and an override below a listed cache price is logged.
- **Superseded (2026-10, see "Pool pricing aligned with personal credit" below):** **Margin at purchase for the pool, markup at usage for personal credit.** Pool credit is `gross / (1 + POOL_MARGIN_BPS)` (8%; the spec's `MARGIN_PERCENT` is accepted as an alias), computed by `poolCreditMicros`, and pool usage is charged at raw cost (markup 0 on pool rows). Personal credit keeps `MARKUP_BPS` at usage: repricing existing balances would contradict Terms §7. **Spec deviation D3, accepted.**
- **Purchases go through one interface (`billing/purchases.ts`).** A checkout names its `target` (`personal` or `pool`), the ledger and the buyer in its metadata (also on the PaymentIntent); sessions from before the pool have no target and credit personally. `fulfilPurchase` is the only place purchase credit is computed: personal credit is the pre-tax amount net of Stripe's fee, as before; pool credit is `gross / (1 + margin)`, with `margin_bps`, `gross_micros` and Stripe's fee recorded on the row (the fee is not deducted: the margin pays it). Both record `user_id`, which the supporter tier reads.
- **Superseded (2026-10, see below):** **Pool purchases start at `POOL_MIN_PURCHASE_CENTS` ($10), so the margin covers Stripe's fee on the pre-tax amount.** At 8%, $10 buys $9.259259 and leaves $0.7407, which covers Stripe's 2.9% + 30¢ ($0.59) and 4.4% + 30¢ ($0.74) on $10; the other presets ($20, $50) leave more (tested). Stripe charges its fee on the total including tax, so a taxed $10 purchase on a 4.4% card (above about $10.02 with tax) costs the operator a few cents more than the margin; pool funds are unaffected. Below $10 the fixed 30¢ would eat the margin.
- **Pool pricing aligned with personal credit (owner decision D4, 2026-10; supersedes the margin-at-purchase bullets above).** A pool purchase is credited the pre-tax amount minus the payment processor's actual fee, through the same `netOfFee` as a personal top-up (`margin_bps` is 0 on new rows). The operator earns a per-call markup instead: pool usage rows carry `markup_bps = POOL_MARKUP_BPS` (default 500, +5%), charged `cost × (1 + fee) × (1 + markup)` by the same `chargeMicros` as personal usage, and pool holds (`worstCaseHoldMicros`, `ceilingHoldMicros`) include the markup so a hold always covers its charge. The $10 pool minimum (`POOL_MIN_PURCHASE_CENTS`) stays as a business choice; it no longer needs to cover a fee. `POOL_MARGIN_BPS`, `MARGIN_PERCENT` and `poolCreditMicros` are gone. See docs/polar-migration/04-verification.md.
- **Refunds and disputes of pool purchases take back the credit-equivalent, clamped to what the pool has (`PoolBank.debit`).** A refund of $X pre-tax requests `X × credit / gross` of the original grant (a $10 refund at 8% requests 9_259_259, not 10_000_000). The debit runs under PoolBank's lock, so it can't push `available` below 0; if the pool has spent the money, the debit takes what is there and the shortfall is the operator's (logged as `pool_debit_shortfall`; the requested amount and shortfall are in the row's note). The row is written even when the clamp leaves 0, so a redelivery, or a later partial-refund event that lists the same refund again, never debits it a second time. A won dispute credits back exactly what the dispute took. Personal refunds and disputes stay unclamped (the user's own balance may go negative, as before), and now record `user_id` and the negative gross.
- **Admins credit without SQL (`POST /api/admin/credit`).** An `adjustment` is a signed `credit_grants` row keyed on `admin:<idempotencyKey>` (a negative pool adjustment goes through `PoolBank.debit`, clamped); it never makes anyone a supporter. A `simulated_purchase` runs `fulfilPurchase` exactly as the webhook would, with no fee and the ref `dev:<key>`, and does count toward supporter status; it exists only where `DEV_PURCHASES_ENABLED` is `"true"` (404 otherwise, as for an unknown route), which `wrangler.jsonc` ships `"false"` (tested).
- **Daily caps are checked inside `reserve`, in this order: the user's replies and spend, the network's, then whether the pool can cover the hold (`empty`), then the tier's global ceiling.** Spend counts settled charges plus pending holds; a released reply gives its request back; topic tagging counts toward no one's caps. `empty` comes before the global ceiling so an empty pool always shows the empty state rather than "busy today". The free tier's ceiling is the lower of `POOL_FREE_DAILY_GLOBAL_MICROS` and `POOL_FREE_DAILY_GLOBAL_BPS` of the day's base: the pool's balance at 00:00 UTC plus what was added to it since, so a pool funded during the day serves free learners at once rather than from the next day. Supporters are not counted against it; they have their own ceiling of the same form (`POOL_SUPPORTER_DAILY_GLOBAL_MICROS`, $10, and `POOL_SUPPORTER_DAILY_GLOBAL_BPS`, 40%). With supporter status for life after any purchase (D5), one $5 top-up per account would otherwise make a farm of accounts an unbounded drain, limited only per network; the separate ceiling keeps the spec's "supporters are not counted against the global ceiling" while bounding them too. (Since [One membership rule: own keys](#one-membership-rule-own-keys-2026-10), there is one tier and one ceiling for everyone: `POOL_DAILY_GLOBAL_MICROS` and `POOL_DAILY_GLOBAL_BPS`, and the per-user caps are `POOL_REQUESTS_PER_DAY` and `POOL_SPEND_MICROS_PER_DAY`.)
- **Superseded (2026-10, see "Two tiers: free and member" below):** **Supporter = lifetime net purchases above $0 (owner resolution of D5).** Net = Σ gross of the user's purchases, personal or pool, minus their refunds and disputes (gross, or for refunds before migration 0010 the refunded amount); admin adjustments and membership credit never count. `SUPPORTER_WINDOW_MONTHS` (default empty = for life) can require the latest purchase to be that recent. Purchases from before migration 0010 have no `user_id` and count through the ledger id `u_<userId>`. Net purchases of a cent or less count as none (`SUPPORTER_ROUNDING_MICROS`): each partial refund's pre-tax share is rounded on its own, so a purchase refunded in full, in parts, can leave a few micro-USD behind.
- **Pool rows carry the caller's user id, branch, cap tier and `ip_key`, a daily-rotating keyed hash of the network** (`HMAC-SHA256(BETTER_AUTH_SECRET, day + ':' + network)`, 16 hex characters, where the network is the IPv4 address or the IPv6 /64). It rotates daily, so it can't link a network across days, and no address is stored.
- **One config module, `src/config.ts`.** Every cap, price, margin, limit and flag is parsed there once per env object and frozen; the old accessors (`usageHoldMicros`, `markupFor`, `membershipCreditCents`, `simpleMaxInputTokens`…) read it. Safety clamps log when they change a value: the call timeout stays a minute under the reservation TTL, the give-up age is at least the TTL, and the impact feed's crowd threshold is never below 3.
- **The pool ships off (`POOL_ENABLED = "false"` in `wrangler.jsonc`, `"true"` in the tests),** so master stays deployable while the pool is built in stages.
- **The server decides who pays, per request (`AccountContext.funding`: `own-key`, `personal` or `pool`).** The Learn app asks with the payment header (`own-key`, `credit` or the new `pool`); the account middleware maps it, and the pool's parameters (model, price, locked prompt, caps, TTLs, the caller's `ip_key`) are resolved Worker-side from `appConfig` into `AccountContext.pool`, which travels to the tree's Durable Object in the send body or as one JSON query parameter. Neither Durable Object reads pool config of its own, so a per-request env (a test's) applies everywhere.
- **Power never uses the pool.** A pool header on a power request is ignored: power is always `personal`. The pool is for Learn, on one economical model; power users choose their models and keys.
- **Pool sends need a signed-in user.** The dev bypass has no user to cap, so a pool request there is pool-funded with nothing to spend (403 `pool_unavailable`).
- **Spent credit falls back to the pool for sends and `context?resolve` only, never for reviews.** One gate (`billing/gate.ts` `assertCanGenerate`) runs in front of the three generating routes: membership, then who pays (a Learn send whose personal `available` can't cover one `USAGE_HOLD_MICROS` moves to the pool while it is on), then the pool's rules or the existing credit, model and rate checks. The route rebuilds its ChatService after the gate, so a fallback's summaries run on the pool too. Reviews are not offered on the pool at all (403 `pool_unavailable` on the pool header): a review is a second opinion from a model the learner picks, which the pool's one-model rule excludes, and a Learn user without credit still gets 402 `payment_required`.
- **On the pool, the server pins the model, the system prompt and the limits, whatever the tree or branch says.** Only the services that generate (the Durable Object's send, `context?resolve`) get the restrictions (`services.ts`, `generating`): a registry with the pool model only (`poolProviderConfig`: context = `POOL_MAX_INPUT_TOKENS` + `POOL_MAX_OUTPUT_TOKENS`, output capped, OpenRouter's `provider.max_price` from the price table), the pool's chat settings (input and output caps; summaries and titles on the pool model), `ChatServiceDeps.pinnedModel` (the reply, budgets, summaries, titles and the assistant node record it; the branch row is untouched) and `systemPromptOverride` (the tree's prompt is replaced in the context, not in the tree). A `pinnedModelRegistry` around the meter rewrites `request.model` as a backstop, and the pool meter prices the pool model whatever the request says. Routes that never generate (`/api/providers`, creating trees and branches) keep the simple config, so a pool session never writes the pool model onto a branch. A message longer than `POOL_MAX_MESSAGE_CHARS` is a 400.
- **The pool's context limit is a hard bound, on every call it pays for.** Its chat service measures budgets in UTF-8 bytes (`ChatServiceDeps.inputBound`, `estimateTokensUtf8` = bytes / 3.5, the same as chars / 3.5 for ASCII), so `POOL_MAX_INPUT_TOKENS` bounds a reply's prompt at 3.5 bytes per "token" in any script. Summary prompts (compaction and summary-mode branches, on a send or `context?resolve`) are clipped to the same limit, keeping the most recent part of the transcript and the start of the excerpt (`buildSummaryPrompt` with a limit). Without that, a long imported node or a long own-key branch could be summarised by the pool in one request of any size, which made the pool a free long-document summariser.
- **On the pool, a branch's anchor quote is quoted user text, at most `POOL_MAX_MESSAGE_CHARS` long.** The quote is client-set free text (up to 10 000 characters, not checked against the branch point), so on the pool it is clipped to a message's length (`anchorQuoteMaxChars`) and rendered as an `<excerpt>` in the user turn, as everywhere (see the prompt caching audit); the system channel holds only the locked prompt and summaries. Checking that the quote is a substring of the branch point was not adopted: Learn quotes the rendered text of a Markdown reply, which is not a substring of its source.
- **The reply is reserved before any node is written.** `TreeSession.send`, inside its send lock and before `beginSend`, reserves the reply's ceiling hold (the pool's input limit in, the output cap out; `poolInputLimitTokens`: 3.5 bytes per `POOL_MAX_INPUT_TOKENS` plus what rendering adds, within the context window, and the meter refuses any call over it) through PoolBank; a refusal is a `PoolBlockedError`, which both the Durable Object and the Worker serialise with `error.pool` (`PoolBlockDetails`: reason, limit, reset time; the supporter, later member, cap is gone since _One membership rule_), so the client sees 402 `pool_empty` (empty, or unpriced), 429 `pool_cap_reached` (caps and rate) or 403 `pool_unavailable`, and the branch is untouched. The reservation id rides on the reply's usage tag; the meter shrinks the row to the exact worst case instead of reserving again. If `beginSend` fails, or the run ends without dispatching the reply, the reservation is released (`releaseUndispatched`, which never touches a dispatched row). There is no route-side balance precheck: the reservation is the check.
- **A refused summary or title never fails a pool send.** Summaries and titles reserve their own exact worst case through the meter; a refused summary is a failed summary (the context falls back to truncation, with a status line), and a refused title keeps the default title.
- **`PERSONAL_CREDIT_ENABLED` (default off) lets personal credit be spent before Stripe is configured** (`personalCreditReady` = billing configured or the flag), so admin-granted credit works while the pool launches first. The pool itself needs only `POOL_ENABLED` and a usable `tangent` provider (`poolAvailable`), never billing.
- **Per-minute rate limits live in PoolBank, not in a rate-limit binding** (`POOL_USER_PER_MINUTE`, 6; `POOL_IP_PER_MINUTE`, 20): fixed one-minute windows per user and per network key in PoolBank's SQLite storage, checked under its lock before the daily caps. So every pool limit is in `src/config.ts`, a test's env applies, and the chat rate limiter's bucket isn't shared. Only replies count (and a `context?resolve`, through `PoolBank.admit`): a reply's summaries, title and tagging ride on the admitted reply. A refusal is 429 `pool_cap_reached` with reason `rate` and the next minute as the reset.
- **Pool limits fail closed.** Where the existing chat and key limiters fail open (a missing binding must not lock users out of their own keys), the pool is the operator's money: if PoolBank's counters can't be read or written the request is refused (`rate`), and an error from PoolBank itself never admits a request.
- **The pool's account gates run in the Worker before anything is written (`billing/gate.ts` `assertPoolAccess`), each a 403 `pool_unavailable` with its reason:** a signed-in user; not `suspended` (`auth_users.pool_suspended`, set by an admin through `PATCH /api/admin/users/:userId`, or by a lost dispute of a purchase); a Turnstile pass on record (`verify`); the account's pool identity (`duplicate_identity`); older than `POOL_MIN_ACCOUNT_AGE_MS` (`too_new`, default 0: farms pre-age accounts, so the age adds friction for learners without bounding drain; the per-network and global ceilings and one identity per mailbox are the real bounds). None of the three columns is a Better Auth field, so no auth endpoint can set them.
- **Turnstile on signup and on first sign-in (owner resolution of D4: both, not only at first pool use).** A magic link can only be requested with a Turnstile pass (Better Auth's captcha plugin), so a magic-link sign-in records `pool_verified_at`. OAuth providers run their own bot checks but not ours, so an OAuth sign-in of a user with no pass on record is redirected, from Better Auth's after hook, through `/verify`: a server-rendered page with Cloudflare's widget and no script of our own, whose form posts the token back; a pass (Siteverify, hostname pinned outside localhost, action `pool-verify`) records it and continues to where the callback was going (same-origin paths only). Passkeys can only be added once signed in, so they never make a first sign-in. Accounts from before the check get the same Turnstile at first pool use (`POST /api/pool/verify`; the pool answers `verify` until then). The interstitial runs only while the pool is on and Turnstile is configured: without the pool there is nothing it protects that the providers' own checks don't, and without a secret every check fails closed anyway.
- **One pool identity per mailbox.** `pool_identity` = SHA-256 of the normalised email (lower-cased, `+tag` stripped; for Gmail dots removed and `googlemail.com` folded into `gmail.com`), unique where set, claimed at the Turnstile pass (or by the gate, for a pass recorded before a claim could succeed). A second account on the same mailbox can sign in and use everything but the pool. Only the hash is stored; it is never shown.
- **A pool identity outlives its account.** Deleting the account and signing up again with the same mailbox must not lift a suspension or reset the day. So `pool_identity_holders` records every account that claimed an identity (the daily `cap_requests`/`cap_spend` count the usage of all of them), and `pool_identities.suspended` holds the suspension per mailbox: the admin PATCH writes it with `auth_users.pool_suspended`, account deletion writes a suspended user's (hashing their email if they never claimed one), the gate refuses either flag, and an admin unsuspend clears both. Account deletion keeps both tables, like the ledger: they hold the hash and user ids, no address.
- **Pool consumption is reported, not just logged.** Every refusal is one JSON log line (`pool_refused`: user, reason, limit), and `GET /api/admin/pool/usage` lists the pool's users over the last days by spend (replies, spend, tagging, last call) and today's network keys by distinct users, which is what an account farm looks like.
- **No OpenAI-compatible endpoint.** The pool is reachable only through the app's own routes (a message on a branch, a context resolve); there is no `/v1/chat/completions` or similar, and request fields outside the app's schema (`model`, `messages`, `max_tokens`…) are dropped by validation (tested).
- **The pool UI shows states, not errors.** Every reply refusal arrives as an HTTP error before any node exists (the reply is reserved first), so Learn turns 402 `pool_empty` and 429 `pool_cap_reached` into an inline notice above the message box (`PoolBlockNotice`: the empty text with **Fund the pool** and **Buy personal credits**, or the cap and its reset; the supporter cap is gone since _One membership rule_) and keeps the message; no toast, no navigation. 403 `pool_unavailable` `verify` opens the first-use check, which links to `/verify` (the apps' CSP doesn't load Turnstile).
- **The meter is public, aggregate and cached.** `GET /api/pool/status` (and the landing page, which reads the same cached value and omits the meter when it can't) shows the available balance as "about N learning sessions" (`POOL_SESSION_ESTIMATE_MICROS` each) plus dollars, and this ISO week's funded exchanges (pool replies settled above 0) and their distinct learners. No user data; one edge-cached D1 batch a minute per pool. Browsers don't cache it (`Cache-Control: no-cache`), so a client read is at most one edge lifetime stale and the post-checkout poll outlasts it. `/pool` states the deployment's margin, minimum, model and caps from the config module, so it can't drift from what the code enforces.
- **Learn picks how to pay; the server still decides.** What replies run on (`PaymentStore.payment`): the own key if chosen; the pool if chosen and on; credit if sold; a saved own key; the pool if on; otherwise the own key. Only an explicit pool choice outranks a saved key (a stale `credit` choice on a server that stopped selling it resolves to the key), and until the key status is known an unchosen payment stays on the own key rather than the pool. The credit/pool switch above the message box appears only while both the learner's own credit (offered and above 0) and the pool can pay; on the pool the Smart/Simple switch is locked to the pool's model. A pool checkout returns with `&target=pool`, so the billing page waits for the pool's meter instead of the buyer's balance.
- **The pool notice is versioned and acknowledged before any pool request.** Its text and version are code (`POOL_NOTICE_TEXT`, `POOL_NOTICE_VERSION` in `packages/shared/src/pool.ts`): changing the text means bumping the version, and everyone acknowledges the new one before their next pool request. The gate checks it after the account gates (403 `pool_consent_required`, `error.consent.currentVersion`), before anything is written or reserved; the version travels in `PoolParams.noticeVersion`, resolved Worker-side (tests raise it with `POOL_NOTICE_VERSION`, honoured only with `TEST_SEAMS`). `POST /api/pool/consent` accepts only the current version (409 otherwise: the client showed an outdated text) and records `pool_consents (user_id, notice_version, acknowledged_at)`, insert-only, so the first acknowledgment of a version keeps its time. Personal credit and own keys never ask. Kept until the account is deleted.
- **Topics are tagged at request time, from the pool exchange alone.** After a pool reply completes (`TreeSession.pump`) on a branch with no tag, `pool/tagging.ts` sends the user message of that exchange, truncated to `classifierInputChars`, to the pool model with a fixed prompt listing the leaf ids. Never earlier messages of the branch, which may have been paid personally or with the user's key, and never the reply. Conversations the pool didn't fund are never classified (the caller checks, the tagger checks again). It runs in the background after the stream, never fails the send, and is retried at the branch's next pool exchange while the branch has no tag.
- **Tagging is charged to the pool through the same reserve/settle flow (PLAN §5), not absorbed in the margin.** The classifier's calls go through the pool meter (`poolGeneratingRegistry`), `purpose: 'tagging'`, at their exact worst case (input bound plus `classifierMaxOutputTokens`, 12), with dispatch stamping, clamping, the breaker and expiry like any pool call; PoolBank counts them toward no one's daily caps or rate limits. An empty pool refuses the reservation and the exchange simply goes untagged (it still counts in the totals).
- **The classifier may answer only a leaf id of the taxonomy (`pool/taxonomy.ts`); anything else is rejected and nothing is stored.** The answer is trimmed and must equal a leaf id exactly: no free text, no unknown id, no parent. Aggregation (S8b) counts per leaf with no roll-up, so a parent is never named because of its children. Rejections are counted in the logs (`pool_tag`), never with the output, which could echo the question.
- **Sensitive topics are stored as the sentinel `sensitive`, never their id.** Health, mental health, sexuality, legal matters, personal finances and religious doubt (and every topic under them) are counted in totals but never named, so the specific id has no use; stored next to `usage_events.user_id` (joined on the branch) it would be a sensitive record about a person.
- **Tag rows hold no text and no user or tree id:** `pool_topic_tags (branch_id, topic_id, branch_depth, created_at)`, one per branch (`ON CONFLICT DO NOTHING`), depth 0 for the trunk. Per-topic learners come from the pool's `usage_events`. The question lives only in the classifier request; a test scans every text column of the tag, consent and usage tables and the logs for it. Account deletion deletes the user's consents and the tags of the branches their usage rows name; the weekly job (S8b) deletes tags 14 days after a branch's last pool use.
- **The impact feed is one immutable snapshot per ISO week, written by a Monday cron.** `17 4 * * 1` runs `aggregatePoolImpact` (`pool/impact.ts`) for the week just ended (Monday to Sunday, UTC); `src/cron.ts` dispatches each cron string to its own jobs, so the 10-minute reconcile never aggregates and the weekly run never reconciles. A snapshot is never rewritten: a re-run (a retried cron) finds it and only repeats the tag retention pass. The snapshot, its named topics and newly queued topics are one D1 batch (a transaction), multi-row inserts chunked under D1's 100 bound parameters.
- **Only funded pool replies count.** The base set is the pool account's `usage_events` with `funding = 'pool'`, `purpose = 'reply'`, `status = 'settled'` and `charge_micros > 0` in the week: released replies never reached the model and settled-at-0 ones cost nothing; summaries, titles and tagging aren't exchanges. Per-topic counts join that set to `pool_topic_tags` on `branch_id`, so a mixed branch's personal or own-key exchanges never count toward its topic, and there is no join through `nodes` or `trees`: a tree deleted mid-week still counts. Learners are distinct `usage_events.user_id`; depth is averaged per exchange.
- **A topic is named only when every rule holds:** a taxonomy leaf (no roll-up, so a parent is never named because of its children); at least `IMPACT_MIN_DISTINCT_USERS` distinct learners that week (default 5, clamped to at least 3); not sensitive (the `sensitive` sentinel, or any id under a sensitive root, is counted in the totals and never named, queued or "deepest"); not on `POOL_TOPIC_BLOCKLIST` (a root id blocks its leaves; blocklisted topics are never queued); and approved. Totals (exchanges, learners, distinct topics, average and maximum depth) count everything. The "deepest rabbit hole" is the named topic with the greatest average depth.
- **No snapshot of a week without funded exchanges.** A week in which the pool funded no reply (before launch, the week the pool was switched on, or a quiet week) writes nothing (`no_exchanges`), and the readers skip a zero snapshot stored before this rule, so the feed never shows "0 exchanges for 0 learners" under a live meter.
- **No snapshot while the pool is off.** Snapshots are immutable, so a weekly run before launch would publish a permanent zero week. While `POOL_ENABLED` is off the job only runs the tag retention pass, and `/api/pool/impact*` answer 404 (the pages already leave the feed out). The first snapshot is of the first week the pool was on; that week may be partial.
- **New topics wait in a review queue; approval applies from the next snapshot.** The first time a topic would be named, the job inserts `pool_topic_reviews (status 'pending', first_seen_week)` instead of publishing it. An admin approves or rejects it on the admin page (`/api/admin/pool/topics`); approved topics publish automatically in later weeks, rejected ones never, and a decision can be changed. Because snapshots are immutable, a topic approved on Tuesday doesn't appear in the snapshot it was queued from. Together with the blocklist and the threshold this keeps a coordinated group of accounts from forcing a crude or spam topic onto the public page.
- **The feed is public and aggregate.** `GET /api/pool/impact?week=YYYY-MM-DD` (latest when omitted; 404 when there is none) and `GET /api/pool/impact/weeks` (newest first, at most 52) are registered before the session middleware and carry no user, branch, tree or pool ids (`Cache-Control: public, max-age=300`). The landing page shows the latest snapshot next to the meter (up to 12 topics), `/pool` shows it in full with a server-rendered list of past weeks (`/pool?week=…`; an unknown week reads "No snapshot for that week"), and the fund section shows it under the meter (`ImpactFeed`); each page renders without it when there is none or it can't be read.
- **Tag retention runs with the weekly job.** It deletes `pool_topic_tags` rows created more than `IMPACT_TAG_RETENTION_DAYS` (14) ago whose branch has had no pool reply since then (`usage_events_branch_idx`, migration 0013, keeps the lookup indexed). A branch used again is re-tagged at its next pool exchange.
- **Featured conversations are a stub, off.** `FEATURED_CONVERSATIONS_ENABLED` is in the config (default and deployed `false`); `featuredEnabled(env)` would also require `DMCA_AGENT_REGISTERED`, because featuring a conversation is publishing user content. `/api/featured` and everything under it answers 404 `not_found` to every method, flag on or off, signed in or not; `MeResponse.featuredConversations` is typed `false`; there are no tables, columns or UI, so nothing is collected. Share links already provide explicit, per-conversation, revocable opt-in; a future wall would flag `shares` rows (DEFERRED).

## Payments behind a port (Polar)

Supersedes the Stripe-specific bullets above (docs/polar-migration/: 01 research, 02 mapping and decisions D0–D15, 03 architecture, 04 implementation notes and sandbox checks).

- **Polar is the merchant of record.** It sells credit and the membership to the user, computes, collects and remits sales tax and VAT, issues invoices and receipts, and handles disputes. Stripe Tax, tax-id collection and our own tax registrations fall away; only income tax remains. Pre-launch, so a hard cutover with no Stripe legacy path (D0).
- **One port, normalised events, stateless adapters.** `billing/payments/port.ts` (`PaymentProvider`) is the only interface between billing and a provider. Adapters (`billing/providers/polar/`, `billing/providers/fake.ts`) translate provider objects into `PaymentEvent`s (`payment.succeeded`, `refund.succeeded`, `dispute.*`, `membership.changed`) and requests into provider calls; they never touch D1, the ledger or business settings. The domain (`billing/payments/apply.ts`) decides. ESLint keeps `@polar-sh/sdk` inside the Polar adapter and adapters out of the ledger; `scripts/check-provider-neutral.mjs` (run by `pnpm lint`) keeps provider names out of the shared packages and the apps.
- **Amounts cross the port as USD cents, pre-tax and tax split by the adapter.** Polar: `net_amount` (never `total_amount`); the fee is `platform_fee_amount`, or a configured estimate (`POLAR_FEE_BPS` + `POLAR_FEE_FIXED_CENTS`, logged `fee_estimated`) rather than throw-and-retry, because Polar disables a webhook endpoint after 10 consecutive failures (D3).
- **Idempotency stays on the provider's object, through `credit_grants.provider_ref`** (renamed from `stripe_ref`): adapters mint `<provider>:<object>:<id>` refs, the domain derives secondary ones (`…:membership-refund`, `…:reinstated`, `…:lost`).
- **Own routes, no Better Auth payments plugin (D2).** `POST /api/billing/checkout` (ad-hoc USD price on a one-time product, `external_customer_id` = our user id, metadata `{kind, target, accountId, userId, v}`), `POST /api/billing/membership/checkout` (a paying member gets the portal), `POST /api/billing/portal` (404 `no_customer`), and the public `POST /api/webhooks/:provider` (403 bad signature, 202 nothing to do, 500 retry).
- **Membership state is ours (D7).** `billing_subscriptions` holds the provider's snapshot (normalised `SubscriptionStatus`, raw `provider_status`, `version` = Polar's `modified_at`), upserted with a version guard so order and duplicates don't matter. `membershipFor` stays one D1 query; no provider call per request. `MembershipInfo.subscriptionStatus` replaces `stripeStatus`.
- **Customers are addressed by our user id;** `billing_customers(provider, user_id, customer_ref)` records the provider's id when an event names it (D6). Account deletion always asks the provider to revoke subscriptions and anonymise the customer, and aborts on failure.
- **Refunds debit only when settled (D10);** disputes are polled from the 10-minute cron because Polar has no dispute webhooks (D5). A lost dispute suspends pool access once (a marker row), so a poll can't undo an admin's lift.
- **Superseded (2026-10-05, see below):** **Pool purchases are gated by `POOL_PURCHASES_ENABLED` (off) until Polar confirms in writing that they are within its acceptable-use policy (D1).**
- **Superseded (2026-10-05, see below):** **Pool pricing is aligned with personal credit (owner decision D4):** purchases credited net of the actual fee, a 5% per-call `POOL_MARKUP_BPS`, $10 pool minimum.
- **What the next switch costs:** a `providers/<x>/` adapter with its fixtures and tests, a literal in `ProviderId`, a case in `payments/index.ts`, its env vars, the legal text and the README. Post-launch, a webhook-only legacy slot for the old provider's refund window.

## Revenue-funded community pool

Owner decision, 2026-10-05; resolves D1 (docs/polar-migration/02-stripe-to-polar-mapping.md, 05-pool-framing.md).

- **Customers can no longer buy credit for the pool.** Tangent sells two things: the yearly membership (with its included credit, none by default since _One membership rule_) and personal credit (top-ups, spent at provider cost + `MARKUP_BPS`). The pool is free credit Tangent provides, an operator expense like a free tier, so Polar's prohibition of "donations, crowdfunding, community access" doesn't arise: every sale is the buyer's own membership or prepaid usage. Removed: `target: 'pool'` checkouts, `POOL_PURCHASES_ENABLED`, `POOL_MIN_PURCHASE_CENTS`, the fund section and `#fund-pool`, `fundingOpen`/`markupBps`/`minPurchaseCents` on `PoolStatusResponse`, `PurchaseTarget`, and simulated pool purchases. A checkout body with `target: "pool"` is a 400; a Polar order whose metadata still says `pool` maps to `unknown` and is never credited.
- **Tangent commits a share of its revenue, `POOL_REVENUE_SHARE_BPS` (default 20%), and the public pages quote it from the config.** Membership: share × (pre-tax amount − Polar's actual fee), granted when the payment is applied (first year and renewals), keyed `<paymentRef>:pool-share`; an unknown fee is retried after the included credit is in. Credit: share × the **markup** part of settled personal charges (`charge × markup_bps / (10000 + markup_bps)` per row), never of the purchase: a $10 top-up nets $9.20 of credit and earns Tangent ≈ $0.84 only as it is spent, so 20% of the purchase ($1.84) would lose money on every top-up. Pool and own-key usage carry no markup or aren't metered, so they never count.
- **The usage share is granted once per completed UTC day by the 10-minute cron (`pool-share:usage:YYYY-MM-DD`), from `settled_at`, not `created_at`.** A settled row never changes, so a day's sum is final once it has ended (plus a 15-minute grace for settles in flight); a call that settles after midnight counts on the day it settled. Every day gets a row, 0 included, so each is decided once; the cron starts at yesterday on its first run and catches up at most 31 missed days. While the pool is off or the share is 0 it still writes each day's 0 row, so re-enabling the pool never back-fills the days it was off (audit R1, docs/polar-migration/06-payment-audit.md). A partial index (`usage_events_personal_settled_idx`, migration 0017) keeps the daily sum off a table scan.
- **Rounding: integer micro-USD, rounded down** (per markup rate for a day), so the pool never gets more than the stated share; the shortfall is under a micro-dollar per rate per day.
- **New ledger kind `contribution`** for the share and its reversals (no DDL: `kind` is plain text). Grants carry no `user_id`, and the (since removed) supporter query counted only `purchase` and `refund`, so the share never makes anyone a supporter. `gross_micros` is the revenue the share is of (the payment's pre-tax amount, or the day's markup).
- **A refund of a membership payment takes back the same proportion of its share** (refunded pre-tax / paid pre-tax, `creditEquivalentMicros`), once per refund (`<refundRef>:pool-share`), through `PoolBank.debit`, clamped like every pool debit. Membership disputes stay with the operator, as for the included credit.
- **Nothing accrues while `POOL_ENABLED` is off or the share is 0.** The operator can always add more with an admin adjustment, including for someone who arranges shared access directly; `/pool` names the operator's contact for that, and sells nothing.
- **Pool replies are charged at their true cost: the pool markup is gone** (`POOL_MARKUP_BPS` removed; new reservations store `markup_bps = 0`). Tangent charging its own pool a markup would only move money between its own accounts. Rows reserved before keep their stored markup when they settle.
- **Legacy pool purchase rows are kept.** Their refunds and disputes still debit the pool through `debitPoolPurchase` (credit-equivalent, clamped), and they still count toward their buyer's supporter status.
- **Terms §7:** the pool is operator-provided at our discretion, funded from our revenue as described on `/pool`, may change or end, and may be empty; credit has no cash value, can't be transferred (to another account or to the pool), and isn't refundable except where the law requires it or under Polar's buyer terms (Polar, as merchant of record, may refund).

## Funding apart from the provider (2026-10)

- **A provider id names only the endpoint, with the same meaning in both apps; who pays is the funding, decided apart from it.** The built-in provider's id was `tangent`, which meant "OpenRouter, paid with Tangent credit" in power and "OpenRouter, paid however this request pays" in Learn, so the same stored branch meant different things per app and metering was keyed on the id. The built-in provider is now the endpoint `openrouter` (`BUILT_IN_PROVIDER_ID` in `@tangent/shared`, the same id as the user's own OpenRouter) on the operator's key; `isMetered`, the 402 balance check, the per-user rate limit, the membership gate and key withholding look at funding only (`isMetered(account, funding)`). This is the "shared core" step towards power and Learn being views of the same data; the accounts stay separate (`p_` / `u_`) and ownership is unchanged.
- **Power's funding is stored per branch (`branches.funding`: `own-key` | `credit`); Learn's stays per request (its payment header).** Power used to choose credit per branch by picking `tangent` (one branch on credit next to one on the user's own OpenRouter key, a reviewer on credit for a branch on an own key), and per-request funding would have lost that choice and changed who pays for existing mixed trees. Learn's payment is the learner's one choice (`own-key`, `credit`, `pool`) plus the server's move to the pool when credit runs out, so it can't be per branch. A review names its reviewer's funding in the request (`ReviewRequest.funding`, default `own-key`) and still checks the reviewed branch's funding for its summaries (`alsoSpendsOn` is now a route).
- **Learn ignores a branch's funding and writes `own-key`** (`ChatServiceDeps.fixedFunding`): one registry serves every route there, on the operator's key exactly when the request pays with credit or the pool. `own-key` is the value that never spends credit, so a Learn tree carried into power (a backup) never starts charging credit on its own.
- **Power resolves `credit` routes in a registry of their own** (`creditRegistryFor`: `builtInPowerConfig` on the operator's key, built without the user's keys, wrapped whole by the meter), and `own-key` routes in the user's registry, which never holds `OPENROUTER_SIMPLE_API_KEY`. `ChatService` picks the registry by the branch's funding (`creditProviders`), so the same endpoint id can be on either key. `/api/providers` lists the built-in endpoint a second time after the own providers with `funding: 'credit'`; the apps key their pickers by `routeKey` (`<id>` or `<id>@credit`), so power still shows "OpenRouter" and "Tangent credit" as two choices: the UX is unchanged.
- **A provider named without a funding is on the user's own key; nothing named keeps the parent's (or the branch's) route.** Naming a provider never spends credit implicitly, the same rule as Learn's missing payment header. A funding named alone keeps the provider. A new tree's default route keeps the old rule (the first usable non-fake own provider, then Tangent credit, else the own registry's default). (Replaced by _Default route of a new tree_.)
- **Credit asked for where it isn't offered is refused (400), never served on another key.** Before, a power `tangent` branch on a server without credit was an "Unknown provider"; now the route has no registry and the same 400 follows. The membership is still asked for first, as before (such a call isn't metered).
- **The legacy id `tangent` is accepted on input as `openrouter` on credit** (`fromLegacyRoute`, applied by the request schemas: trees, branches, reviews), for clients built before the change. That is what it meant in power, and Learn ignores the funding anyway. `SIMPLE_PROVIDER` may still name it (read as `openrouter`); `PROVIDERS` may not use it, since requests still name it for the built-in endpoint. A summary provider named `tangent` (`SUMMARY_PROVIDER_ID`) means none; any other summary provider is looked up among the own-key routes only, so summaries of own-key branches never cost credit.
- **Migration 0020 (`branch_funding`) adds `branches.funding` (default `own-key`) and renames stored `tangent` ids to `openrouter`** in `branches`, `nodes` and `summaries`. Usage rows keep the provider id they recorded: they are billing history.
- **The rule for data that doesn't say who paid: power `tangent` branches become `credit`, everything else `own-key`.** A power branch on `tangent` was on credit by definition (it is in a tree whose account row has `mode = 'power'`). A Learn branch on `tangent` doesn't record who paid (it depended on each request's payment header) and Learn ignores the field, so it gets the safe `own-key`; so does a branch of a tree whose account row is missing (unreachable data). Backups made before the change carry no funding and don't say which app they came from, so import reads a missing funding as `own-key` and `tangent` as `openrouter`: an imported conversation never spends credit until its owner picks Tangent credit for it (branch settings). The in-browser demos read sessions saved before the change the same way. A reviewer saved in the power app's settings as `tangent` (localStorage) is read as `openrouter` on credit, which is what it meant there.
- **Each reply still records only the endpoint and model it ran on** (`ChatNode.providerId`); its funding is the branch's (power) or the request's (Learn), and the ledger's usage rows say what was charged. Shares and exports carry neither.

## API errors in the clients (2026-10)

- **The web clients map a 401 by its error code, not its status.** `ApiClient` used to turn every 401 into "Your session has expired", so a `key_required` (no usable API key) read as a lost session and the apps' key dialogs never opened. Now only `unauthorized`, or a 401 without our JSON error body (a proxy), is "session expired" (`isSessionExpired`, which `AuthService` uses to send the browser to the login page); every other 401 keeps its code and the server's message. One fix in `@tangent/web-shared` covers Learn, power and Canvas.
- **Learn's key-required message names OpenRouter** (`LEARN_KEY_LABEL`, the `keyLabel` of `assertGenerationAllowed`). Learn's provider is labelled "Tangent", but its own-key route runs on the user's OpenRouter key, so "Add your Tangent API key" asked for a key that doesn't exist. Power keeps the provider's label, which is the key's name there.

## Fake reply removed (2026-10)

- **Power no longer offers the offline fake provider ("Fake (offline)", which answered "Fake reply (…) to N message(s)").** The in-browser demos (`/demo`, `/learn/demo`, `/canvas/demo`) now show the app without keys or a model, so a provider that only echoed the prompt was a confusing choice in the real app. It is gone from `DEFAULT_PROVIDER_CONFIGS`, so `/api/providers` never lists it and no new branch can use it.
- **The `fake` kind stays, as a test seam.** The worker and core suites run on it (configured explicitly in `PROVIDERS` / `SIMPLE_PROVIDER`, `apps/worker/vitest.config.ts`), and so do `scripts/smoke.sh` and the offline built-in provider of `.dev.vars.example` ("Option C"). It is never a default: a deployment offers it only if its operator configures it. The registry and `ChatService` keep skipping it for the default route and auto-titles.
- **Branches stored on `fake` move to OpenRouter on the user's own key (migration 0021, `retire_fake_provider`), rather than a read-time fallback.** Left alone, every send on them would be a 400 "Unknown provider", from the gate (`assertGenerationAllowed`) before `ChatService` ever saw the branch, and a fallback would have to be repeated in both and in the branch settings the clients show. The target is `openrouter` with `deepseek/deepseek-v4-pro` (`DEFAULT_SIMPLE_NORMAL_MODEL`, the default model of power's default OpenRouter, which takes any model id) and `own-key`: OpenRouter is the one key both apps share, and a branch nobody chose to pay for must never start spending credit. Without that key, the next send asks for it (401 `key_required`), and the branch settings can pick another provider. A deployment whose own `PROVIDERS` has no `openrouter` gets "Unknown provider" there instead, as before the migration, and fixes it the same way.
- **Replies keep the provider they ran on.** `nodes.provider_id` = `fake` is history, like the usage rows, and nothing routes by it. Cached summaries made by the fake are keyed by its model, so nothing reads them again.
- **Nothing else stored needs a change.** The power reviewer saved in the browser (`tangent.settings`) is already read leniently: a saved provider that `/api/providers` no longer lists falls back to the branch's provider (`ReviewStore.defaultReviewer`). `account_settings` holds no provider. A JSON backup made before this keeps `fake` on import, like any provider the importing server doesn't offer; picking a provider in Branch settings fixes it.

## Import and export in Learn (2026-10)

- **Learn exports and imports power's JSON backup, unchanged (`tangent-tree-backup` v1, `GET /api/trees/:id/backup`, `POST /api/import`).** One format means a file from either app imports into the other. No new route: the request's mode header picks the account, so an import from Learn lands in `u_<userId>` and one from power in `p_<userId>` through the existing ownership (`ChatService` stamps its own account on the restored tree). Power had no "export everything", so neither has Learn.
- **Learn fetches the backup and saves it from memory (`ApiClient.backup`, `backupFile`, `SAVE_FILE` in `@tangent/web-shared`) instead of power's plain download link.** A link sends no `x-tangent-mode` header, so the server would look for the lesson in the power account and answer 404. The file name is the server's (`backupFileName` in `@tangent/shared`, which the Worker's `Content-Disposition` uses too).
- **An import into Learn is adapted server-side, by `adaptBackupForLearn(backup, target)` in `@tangent/core`** (`packages/core/src/learn-import.ts`), a pure function that `ChatService.importBackup` applies when `ChatServiceDeps.adaptImportsForLearn` is set. The Worker sets it for every Learn account (`services.ts`), and the Learn demo backend sets it too; power never does, so power imports are unchanged (including that they don't check providers: a backup naming a provider the server lacks keeps it, and Branch settings fix it). Applying it in the service rather than the route means any import into a Learn account is adapted the same way, whoever calls it: a later "Create a copy in Learn" for a power tree can export with the power service and import with the Learn one. The target comes from the Learn service itself: its registry's default provider, that provider's models and default model, and the prompt a new tree in that account gets.
- **The rule, per branch: a branch Learn can't run moves to Learn's provider on its default model (Smart); one already on Learn's provider with one of its models (Smart or Simple) keeps it.** "Can't run" is another provider (`anthropic`, `openai`, a test provider), or a model Learn doesn't list (power's open OpenRouter models); the legacy `tangent` id counts as `openrouter`. Smart rather than Simple because a power conversation comes from a model the user picked, usually a strong one, and Smart is also what a new lesson starts on; the Smart/Simple toggle changes it per branch.
- **Every branch becomes `path` context.** Learn shows each side question as its whole path and has no context-mode control, so a `summary` or `independent` branch would answer from context the learner can't see, and summary mode would make summary calls the learner never asked for. `path` is compositional, so with every branch on it the model sees exactly the messages on screen (compacted only by Learn's input cap, as for any lesson).
- **The lesson gets Learn's prompt, not the tree's: the account's saved one, else Learn's built-in one (`SIMPLE_SYSTEM_PROMPT` when set).** That is what a new lesson gets. Keeping a custom power prompt was rejected: Learn has no prompt editor, so the learner could neither see, change nor remove it, and the tutor prompt is what writes the `<tangents>` block that Learn turns into buttons (a pool reply replaces the prompt anyway). The original stays in the power tree and in the file. This breaks "trees keep the prompt they were created with" only in the sense that the import is a new lesson.
- **Funding: every branch is `own-key`, and nothing is spent by importing.** Learn already ignores branch funding and writes `own-key` (`fixedFunding`), so a power branch on Tangent credit doesn't carry its funding over; the adaptation says so too, so the function never moves anything onto credit or the pool even outside Learn's service. Replies after an import are paid however that Learn request pays (own key, credit or pool), exactly like any other lesson. The import itself calls no model.
- **Everything else is kept:** messages, titles, anchor quotes, the tree's structure, the private flag (invisible in Learn, but kept so a round trip back to power keeps it) and the provider and model each reply ran on (history, like usage rows). Adapting is idempotent, and a Learn backup imports into Learn as it was (apart from a prompt the operator has changed since) and into power as it is.
- **Both apps read the file with `readBackupFile` (`@tangent/web-shared`, moved from the power app), which refuses before uploading:** an empty file, one over `MAX_BACKUP_BYTES` (50 MB, far above a long conversation and below what a browser parses comfortably), one that isn't JSON (with a hint that Markdown and HTML exports can't be imported), JSON that isn't a backup, a backup from a newer format version, and a damaged one (the first schema problem), each with a message naming the file. The server still validates (`treeBackupSchema`), so the check is for clear messages, not for safety.
- **Learn's UX:** **Import** next to the "Your lessons" heading (a file picker; the lesson opens after importing, with a toast), and an **Export** download icon next to **Delete** on each lesson and in the open lesson's header. No menus or options: a backup is always the whole lesson, as in power.
- **The Learn demo offers both.** Its in-browser backend already answered the backup and import routes, and Learn's export goes through the API transport (`API_FETCH`), so it works without the server. The power demo still hides Export, whose plain links would reach the real server.

## Read-only power without a membership (2026-10)

> **Extended to Learn (2026-10-07, [One membership rule: own keys](#one-membership-rule-own-keys-2026-10)).** Learn on the user's own key now needs the membership too, so `membershipNeededFor` is `['own-key']` in both apps where the membership is required ("Learn gets none" below no longer holds), and Learn's blocking `MembershipGate` is gone too: a Learn learner on a locked own key keeps reading, and the composer (or the new lesson's **Start lesson**) gives way to `KeyLockedNotice`, with one-click ways out (subscribe, **Continue on the open pool**, **Continue on Tangent credit**; `AccountStore.continueOn`), which bring back a message the server refused. A prompt at the moment of the forbidden action, not a wall over the app. The power and Canvas rules below are unchanged.

- **Without a membership, power is read-only exactly where generating would need one: a branch whose funding is in `MeResponse.membershipNeededFor` while `membership.status` is `inactive`.** In practice that is a branch on the user's own keys (`own-key`) when the fee is on and the membership has lapsed, was cancelled or never existed. A branch on Tangent credit keeps its composer (credit already paid for stays spendable, see _Two tiers_), and so does everything wherever no membership is required. The rule is per branch rather than per account because it is the server's: the membership is asked for per call, by funding (`needsMembership`), so a power-wide lock would refuse what the server allows and a lock on nothing would let users write messages that are refused. It reads simply in the UI: "this conversation is on your own key, which needs the membership".
- **The server states the rule; the clients don't copy it.** `GET /api/me` sends `membershipNeededFor`: `needsMembership` asked of each funding (`membershipNeededFor` in `billing/gate.ts`), and nothing at all when `membership.required` is false, so the fee off, a server without billing (self-hosted: no payment provider sells the membership) and the dev bypass never show anything read-only. Learn gets none. The clients combine it with the live membership (`lockedFundings` in `@tangent/web-shared`), which the billing page's summaries keep current (a code redeemed there lifts read-only at once). No new copy logic, and a copy and an import of the same backup are the same lesson.

The power tree is only read. Power mode only (a request with Learn's mode header is 400: Learn has no power tree to name), same-origin only (`sameOriginOnly`, as it writes into another account of the user), behind the session like every owner route. A second copy makes a second lesson, as importing a file twice does.

## Grounding (web search)

The point of Tangent is to drill deeper and deeper; the deeper a learner goes, the further they leave what the model reliably knows. Grounding replies in a web search is therefore a requirement for a learning product, and the design is about when to pay for it. On the Learn models a search costs far more than a reply, so cost depends on how often we search, not on how much each search costs. Research in RESEARCH ("Web search").

- **OpenRouter's web search, not a separate search provider (Brave, Exa direct).** OpenRouter folds the search fee into the cost it reports for the generation (`usage.cost`, `/generation` `total_cost`), so the existing meter and ledger bill it with no new provider, key, ledger entry or reconciliation path. A dedicated provider would be cheaper per search (Brave about $0.005 against Exa's about $0.007) but would add a second integration and its own metering. The owner chose the simpler route and the extra cost.
- **The `openrouter:web_search` server tool, not the `web` plugin or the `:online` suffix.** The plugin runs one search on every request, and OpenRouter picks the query from the conversation; in a branch the last message is often just "why is that?". With the tool, the model writes the query and decides whether to search at all. If the beta tool doesn't hold up, falling back to the plugin is confined to `webSearchBody` in `openai-compatible.ts`.
- **A free gate decides whether to offer the tool; the model decides whether to use it.** `decideGrounding` (`packages/core/src/grounding/policy.ts`) is a pure, deterministic score with no I/O and no model call:
  - depth ≥ 2: +2; depth 1: +1;
  - a specific fact (a year or date, a number with a unit, "how many", "who invented"…): +2;
  - recency words: +2;
  - sources asked for: +2;
  - two or more named entities: +1;
  - context summarized or compacted: +1;
  - a purely conceptual "why / explain" question with none of the above: −1.

  At 2 or more, the tool is offered. Depth weighs most because tangents are, by design, the deeper layers, edge cases and history where recall is thinnest.

- **Rejected: a classifier call with the summary model.** It adds a reasoning model's latency to every turn, and its judgement is no better than the answering model's, which already has the whole context.
- **Rejected: searching every turn.** Most turns are conceptual explanations a search doesn't improve, and a lesson would cost about 15× as much.
- **At most one search per reply (`max_uses: 1`), and Exa is pinned (`GROUNDING_ENGINE=exa`).** This is the real cost bound. Pinning keeps the price predictable when a power user's model would otherwise switch to native search at a different price.
- **"Check sources" forces a search (`ground: 'required'` on a send) and adds the check to the conversation.** On the branch's last reply the check is appended in place; on an earlier reply it opens a `path` branch, so later messages keep their place. A check is a turn like any other, so later context and child branches inherit its corrections; an ephemeral side panel would lose them. It always works on a provider that can search, whatever the branch setting or the daily cap.
- **Citations are carried forward as Markdown links in the reply, with no KV cache and no raw result text in context.** The grounding instructions ask the model to cite each claim inline and to rely on facts already cited earlier in the conversation; summaries are told to keep the links. This is what stops follow-ups and child branches from searching again. A query cache would rarely hit when the model writes the queries, and would save only about $0.007 on a hit. Excerpts (300 characters) are stored on the node for the UI only.
- **`nodes.sources` is null when the reply didn't search and `[]` when it searched but cited nothing.** The UI needs both, to show "From the tutor's own knowledge" or "Searched the web; no sources cited". Shares and exports carry URL and title only.
- **Daily cap on automatic searches, on Tangent credit only (`GROUNDING_AUTO_DAILY_CAP`, default 40).** It is counted from `usage_events.web_searches` since 00:00 UTC; at about $0.008 a search to the user, the worst case is about $0.33 a day. Own keys are the user's own spend. The count is approximate: a row records its searches when it settles, so replies still in flight are not counted yet.
- **Power gets a per-branch setting (`branches.grounding`: `off | auto | always`, default `auto`), inherited when branching.** Learn ignores it (`ignoreBranchSetting`): there the pedagogy is the operator's, as with the prompt.
- **`GROUNDING` is the operator's ceiling over both apps:** `auto` / `always-offer` / `explicit` / `off`. An unknown value means `off`, so a typo fails cheap.
- **OpenRouter-backed and Anthropic providers can search (`options.webSearch`, `ProviderCapabilities.supportsWebSearch`, `ProviderInfo.webSearch`).** It is set on the built-in provider and on power's default `openrouter` and `anthropic` configs; an operator's `PROVIDERS` entry opts in explicitly, and a hostname check would miss an AI Gateway URL. Anthropic uses its own `web_search_20250305` server tool (about $0.01 a search plus the results as input tokens, on the user's key): the basic variant runs on every Claude model, `tool_choice` stays `auto` because current models reject a forced tool (Check sources relies on its instructions), and since Anthropic reports no cost, it belongs on own-key configs only, never a metered one. OpenAI's native search is deferred.
- **A provider that rejects the tool (4xx `invalid_request` before any text) is retried once without search,** with a status line saying so. A model without tool support then still answers.
- **Summaries, titles and reviews never search.** Only replies go through the gate.
- **The grounding instructions go after the history, not in the system prompt.** When a reply is offered search, `GROUNDING_INSTRUCTIONS` (or `CHECK_SOURCES_INSTRUCTIONS`) travel as `GenerateRequest.turnInstructions`, tagged `<instructions_for_this_reply>`, and the provider appends them to the reply's user turn (`withTurnInstructions`, prompt-cache.ts): on a model with explicit cache markers (Claude) as a separate text part after the breakpoint, elsewhere at the end of the text (automatic caches match by prefix). The system prompt and the history are then the same on every turn, searched or not; and since the next turn sends that user message without them, the entry this turn writes still covers it. Live on `anthropic/claude-sonnet-5.5` (2026-10-08): a turn with the instructions after the breakpoint, then the next turn without them, read 3,187 of 3,212 input tokens from the cache; with the instructions merged into the marked text it read only the system prompt (1,372). A trailing message of its own was not used: not every provider accepts two user messages in a row, and a late `system` message is hoisted into the system prompt on Anthropic.
- **The tool itself still comes and goes with the gate; `tool_choice: "none"` does not keep it in place (tested live 2026-10-08, not adopted).** The idea was to send the tool on every turn and pass `none` on turns the gate says no, so the tool block (which sits before the history in the providers' templates) never changes. On `deepseek/deepseek-v4-pro` OpenRouter drops the tool when the choice is `none`: the prompt is 3,524 tokens with `none` and without the tool, 4,170 with `auto`, so the prefix changes anyway (an `auto` turn after a `none` one read 1,024 cached tokens, about the system prompt). On `anthropic/claude-sonnet-5.5` the tool stays in the prompt (6,627 tokens with `none` and `auto`, 5,711 without the tool) and an `auto` turn after a `none` one read 6,623 cached tokens; but every `none` request on a question that invites a search (4 of 4, streamed or not) failed with 502 `Server tool "openrouter:web_search" failed: upstream returned an invalid response`, while conceptual questions passed (3 of 3). Neither `none` call searched or was charged for one (no annotations, no `server_tool_use`, `usage.cost` equal to the upstream inference cost); an `auto` call that searched cost $0.007 more than its inference. So under `auto`, a turn that gains or loses the tool still misses the cache past the tool block; `always-offer` keeps it stable at the cost of more searches.
- **No web search on the community pool.** A pool call's hold is its exact worst case priced from tokens, and a pool charge is clamped to the hold, so a search fee would land as operator-paid overage. The pool's chat settings turn grounding off, its meter strips `webSearch` from any request, and **Check sources** is refused (400) on pool-funded sends. Adding the search fee to the pool's worst case is in DEFERRED.
- **The daily cap follows metering (`isMetered(account, funding)`):** Learn on credit and power branches funded by `credit`; own-key routes are uncapped.

## Links between messages (2026-10)

Learners notice that a message in one tangent relates to one in another; the tree only records where a branch came from. A link records the other kind of relation. Plan in PLAN §17.

- **Stored directed, shown on both ends.** `node_links` keeps `source_node_id` (where the link was made from) and `target_node_id`, so provenance survives, but every app lists a link under both of its messages: "related" is symmetric to a reader. The pure helpers (`packages/core/src/links.ts`) index links by either end.
- **One link per pair of messages, whichever way round.** `pair_key` (`min|max` of the two ids, written by the repository) is UNIQUE, so linking a pair again, or from the other end, changes nothing: `POST /api/links` answers 200 with the existing link instead of 201 (a concurrent duplicate insert is caught the same way). The second note is not merged in; editing the existing note is the way to change it. A link to itself is refused by the request schema and by a `CHECK`.
- **Messages only, not branches.** Every link joins two nodes. "Link this tangent" links the branch's first message, and the apps show such an end as "Tangent: ‹title›" (`describeEndpoint().isTangentHead`), so one model covers both and a link survives the branch being renamed. An empty branch has nothing to link yet.
- **Same tree only.** Both messages must be in the same tree (400 otherwise). Cross-tree links would need their own ownership and lifecycle rules (two trees, possibly two deletions, and Learn and power being separate accounts), for little gain while a learner's topic lives in one tree. DEFERRED.
- **Links go with their messages.** Deleting a branch deletes the links touching its subtree's messages in the same batch (explicitly, besides the node FKs' `ON DELETE CASCADE`), and deleting a tree deletes all of them. No link ever points at a missing message, so clients never filter dangling ends.
- **Owner data, like private branches: in JSON backups, not in shares or exports.** A backup carries `links` (optional in the schema, so older backups still import) and import remaps them onto the new ids; a link whose ends aren't both in the backup, a self-link or a repeated pair is dropped rather than failing the import, since links are only cross-references. Copy to Learn is an export and an import, so it carries them. Shares and Markdown/HTML exports show the branch structure and leave links out: a note is the learner's private aside, and a link into a branch the share doesn't include would dangle. DEFERRED.
- **No gate.** Creating, editing and deleting a link never calls a model, so it needs no membership or credit and works on read-only power branches; ownership is checked through the messages (`getOwnedNode`) and, for an existing link, its tree, so another account's ids are 404 like everywhere else.
- **Bounded.** At most `MAX_LINKS_PER_TREE` (1000) links per tree (400 beyond, checked before inserting) and notes of at most `MAX_LINK_NOTE_CHARS` (500), blank stored as null. The cap keeps `TreeDetail` and backups small and the picker's index cheap.
- **`origin` is reserved for suggestions.** Every link is `user` today; `ai` is in the schema so model-suggested links can arrive without a migration. Nothing reads links into the model's context yet (DEFERRED).
- **No realtime.** Like the branch structure, links reach other tabs on the next load of the tree; the API returns the created or updated link and each app updates its own copy of `TreeDetail`.

## One membership rule: own keys (2026-10)

Owner decision, 2026-10-07. Supersedes [Two tiers: free and member](#two-tiers-free-and-member-2026-10) and extends [Read-only power without a membership](#read-only-power-without-a-membership-2026-10) to Learn. No migration or grandfathering: there are no users besides the owner.

- **The membership is required for generating on the user's own keys, and for nothing else.** With `ANNUAL_FEE_ENABLED` on (and a provider that sells the membership), a generating call on own keys answers 402 `membership_required` without a paid or waived membership, in Learn, power and Canvas alike. `needsMembership` asks only about the `own-key` funding, so `MeResponse.membershipNeededFor` is `['own-key']` in both apps wherever the membership is required, and empty wherever it isn't. This explicitly reverses "Why BYOK stays free" (_Two tiers_): Learn on the user's own OpenRouter key was free; it now needs the membership like power.
- **Tangent credit is for everyone.** Buying it (`POST /api/billing/checkout`) and spending it need no membership, and it pays anywhere: Learn on either model (Smart or Simple), power and Canvas on any OpenRouter model. Replaces "buying credit stays members-only".
- **The open pool has one set of caps, the same for everyone, paying or not.** It stays Learn-only: power mode and Canvas can never use it. It keeps all of today's free limits: 30 replies and $0.10 a day per user (`POOL_REQUESTS_PER_DAY`, `POOL_SPEND_MICROS_PER_DAY`), under one daily ceiling for all users together, the lower of `POOL_DAILY_GLOBAL_MICROS` ($5) and `POOL_DAILY_GLOBAL_BPS` (20%) of the day's base. The member tier is gone: `POOL_MEMBER_*`, the member tier's own ceiling, `member`/`memberLimit` on `PoolBlockDetails` and `member` on `PoolMeResponse`, and "members get higher limits" on the cap-reached notice. The remaining caps drop `FREE` from their names (`POOL_FREE_REQUESTS_PER_DAY` → `POOL_REQUESTS_PER_DAY`, and likewise the spend cap and the global ceiling), since there is no other tier to tell them from.
- **No credit comes with the membership: the $2 of included credit is dropped.** `MEMBERSHIP_CREDIT_CENTS` defaults to 0 and `wrangler.jsonc` sets `"0"`. The mechanism stays (a grant per paid membership year, taken back once if that payment is refunded), for an operator who wants it. Replaces "the included credit is the sweetener instead of a lower price".
- **Why (the owner): simplicity, and everyone pays a fair amount for what they use.** The $10/year membership is how Tangent earns from bringing your own key; the 10% markup is how it earns from credit. A member who also buys credit pays both, each for what it covers. Rule of thumb for choosing: at +10%, $10 is the markup on about $100 of AI spend a year, so a light user does better on credit and a heavy user on their own key with the membership. The pool exists for people who can't pay. Paying doesn't buy more of it, which keeps it honest and bounds what it costs. The previous scheme's worst gut-check failure was "pay $10 to be allowed to buy credit"; that is gone.
- **The accepted trade.** A Learn user on their own key without a membership is worse off than before: that used to be free. Without a membership they can still learn from the pool within its caps, or on credit. One rule across both apps was judged worth it.
- **Unchanged:** credit already held stays spendable after a membership lapses (now true for everyone, since nobody needs a membership for credit); reading, exporting, deleting, settings, copying to Learn and links never need a membership; waivers; the revenue share (20% of each membership payment after fees, and of the markup on credit as it is used); `ANNUAL_FEE_ENABLED` defaults to off, and with it off nobody needs a membership.
- **Follow-ups (2026-10-07).** No membership where own keys can't be stored: the membership's only job is unlocking own keys, so without `KEY_ENCRYPTION_SECRET` `membershipRequired` is false (whatever `ANNUAL_FEE_ENABLED` says), and neither the apps nor the public pages show or sell it. A new power tree whose own keys are locked starts on Tangent credit only when credit can pay or can be bought (`DefaultRouteFacts.creditBuyable`: credit offered and top-ups sold); where credit only comes from operator grants, an empty balance is a dead end, so it starts on the locked own key, which leads to the membership. With no included credit, a membership payment still grants the pool's revenue share, so a refund that arrives before its payment waits for it (`grantsOnPayment`) and then takes the share back, rather than being acknowledged as nothing to undo. Where the pool is off and no credit is sold, a Learn user without a membership has no way to get replies but the membership: intended, and the public pages say so (no "Create a copy in Learn" promise, no "Free on your own key").

## A missing own key is a choice, not a wall; a refused message is never lost (2026-10)

- **A branch's route (provider, who pays, model) is where it starts, not a lock.** The server always accepted a change (`PATCH /api/branches/:id`, checked by `requireProvider`; each send is gated on the branch's current route), but the power app only showed it in Branch settings and the branch dialog. A bar under the message box now shows the open branch's route and opens its settings; on the user's own key with no key saved in this browser (another device, or it expired: the key lives in that browser's cookie), it says so before anything is sent, with **Use Tangent credit** and **Add your key**. "Branch from here" no longer preselects a parent route whose key is missing: it starts on the default route of a new conversation, keeping the parent's model where that route serves it.
- **The keys dialog a refused send opens (401 `key_required`) offers the way on.** On top: the message wasn't sent, why, and **Continue on Tangent credit** where credit can carry on (`switchToCredit`, then the message is sent there); saving the key sends it too. The power app and Canvas share the notice (`KeyMissingNotice`, `BlockedSend` in web-shared). Learn's "How replies are paid for" says the same when a key-refused message waits, and saving a key or picking credit or the pool sends it (`LessonStore.resumeUnsent`).
- **Message boxes keep their text until the message is in the tree.** The composers (power, Learn, Canvas lanes) no longer clear on Enter: they clear when the reply starts (`UiStore.markSent`), and only if the text is unchanged. Any failure before that (no key, no credit, no membership, the pool's checks, a network error, 409) leaves the text, and a message sent from elsewhere (a tangent, "Ask your own", the branch dialog's starting message, a new conversation's first message) comes back in its branch's box (`unsentDrafts` / `unsentDraft`, the box takes it when empty). Drafts are kept in memory, not in storage: a reload still loses an unsent message.

## Learn tiers: Normal and Max (2026-10)

Owner decision, 2026-10-08: make the cheaper tier smarter and the expensive one a top model, and rename them, since the cheaper one is no longer "simple".

- **Normal is `deepseek/deepseek-v4-pro` (the default), Max is `anthropic/claude-sonnet-5.5`** (`SIMPLE_NORMAL_MODEL`, `SIMPLE_MAX_MODEL`). _Since_ Hosted models from the eval _below: Normal (and the pool and background calls) is `deepseek/deepseek-v4.1-flash`._ Smart becomes Max and Simple becomes Normal as names, but the old Smart lessons were on Pro, so they read as Normal now: same model, same cost. Branches store model ids, never labels (`branches.model`, `nodes.model`, `summaries`, `usage_events`), so the rename needs no data change for them.
- **Tiers are data, not labels.** `ModelInfo.tier` (`normal` | `max`) marks them in the built-in provider's config, in power's suggestions and on Tangent credit (`builtInPowerConfig` keeps it); clients key on it, never on a label. A `SIMPLE_PROVIDER` override may name its tiers with a per-model `tier` key; when none does, its default model is Normal and it has no Max (a pre-tier override listed `[Smart, Simple]`, cheaper second, so position must never name Max). All user-facing wording comes from `@tangent/shared` `tiers.ts` (`TIER_LABELS`, `maxUsageNote`, `compareUsageNote`), so the Worker's pages, Learn and power say it the same way.
- **The legacy `SIMPLE_SMART_MODEL` is read as Normal's fallback, never as Max.** Its deployed value was Pro, Normal's model; no old variable may ever put a deployment on the expensive model by accident. `wrangler.jsonc` sets the new names.
- **Summaries, titles and the open pool's default model stay on Flash (`SIMPLE_FAST_MODEL`), which is no tier.** A background job with a low quality bar, where cost matters. `simpleFastModel` no longer looks at the tier list (it used to fall back to the second model, which would now be Max); with an override, it is `SIMPLE_FAST_MODEL` when the override lists it, else the override's default. Where Learn's config doesn't list the pool model, the pool calls it **Lite** (`POOL_MODEL_LABEL`).
- **Migration 0025 (`learn_tiers`) moves Learn branches on Flash to Pro.** _Revised before it was deployed (see_ Hosted models from the eval_): it moves Learn branches on V4 Flash or V4 Pro to V4.1 Flash._ Flash is no longer one of Learn's models, so every send on such a branch would be a 400. Only trees of `simple` accounts; power branches on Flash (credit and power's OpenRouter take any model) are untouched, and replies keep the model they ran on. Data-only, like 0021.
- **The Max usage note: "Max uses about N× as much as Normal."** `GET /api/providers` sets `ModelInfo.usageFactor` on the Max model of each entry listing both tiers (`withUsageFactors`, apps/worker/src/tiers.ts), from the price table (`modelPrice`: the synced OpenRouter list price, else the built-in placeholder, else `MODEL_PRICES`): `usageFactorOf = max(1, round((10·in_max + out_max) / (10·in_normal + out_normal)))`, input weighted 10:1 because a tutoring turn resends the whole conversation. With Pro ($0.955/$1.911 vs $2/$10 per MTok) that was about 2.6, shown as 3; with V4.1 Flash ($0.15/$0.60) it is about 14.3, shown as 14. Without a price it falls back to `MAX_USAGE_FACTOR_FALLBACK`, the default models' factor (now 14; a Worker test checks it against `DEFAULT_MODEL_PRICES`). Sonnet 5.5 is in `DEFAULT_MODEL_PRICES` (and Pro's placeholder refreshed) so the daily sync tracks both. Approximate on purpose: users pay the reported cost, never this number.

## Compare (2026-10)

"Ask Normal and Max, keep one": both models answer the same question and the user picks the answer that enters the conversation. Contract in `packages/shared/src/compare.ts`.

- **Nothing enters the tree until the pick, enforced by the server.** `POST /api/branches/:id/candidates` streams one candidate (the client runs one request per model), straight from the Worker like a review: no Durable Object run, reconnect or snapshot. The context is planned as if the question had been sent, on the candidate's route and model; nothing is persisted. Summaries are resolved and cached as for a send, on the branch's own route and model (or the summary provider), never the candidate's, so the two candidates share them and Max never re-summarizes on the expensive model. The commit (`POST …/candidates/:candidateId/commit`) appends the question and the server's copy of the answer, with its real model, provider, usage and sources; the branch's own route and model don't change.
- **Finished candidates are held in the tree's Durable Object for 30 minutes** (`CANDIDATE_TTL_MS`, `ctx.storage` under `candidate:<id>`, expired ones pruned on each hold), and the commit runs under the DO's send lock, so no send slips in between "the branch hasn't moved on" and the append. The auto-title of a first exchange (a model call) runs after the lock is released (`appendCandidate`, then `titleCommitted`), so other sends in the tree never wait on it. 410 when a candidate expired (or the DO was reset), 404 for another account's or another branch's, 409 when the branch moved on or a reply is streaming. A commit drops the candidate and its siblings (the other answers to the same question); an unpicked one just expires, so there is no discard route.
- **Both candidates are metered** (each a `reply` usage row with no node), so comparing uses both models' usage, and the apps say so before anything is asked (`compareUsageNote`). The gate treats a candidate like a review (`purpose: 'compare'`): the allowlist bounds the client's model (in Learn: its two tiers, on its own provider only), the branch's route is checked too for its summaries, and it never moves to the open pool. **Compare is refused on the pool** (403 `pool_unavailable`, both routes): the pool's holds are sized for one reply on its one model.
- **Credit holds are per model.** A credit call holds its worst case at its model's price (input bound and output cap, with the fee and the markup), never below `USAGE_HOLD_MICROS` ($0.02); the price is the configured one, else the list price the daily sync stores for every OpenRouter model, and a model with neither is refused on credit. A reply is reserved at `USAGE_HOLD_MICROS` before its nodes are written (402/429 then), and the meter reprices that row to its worst case once the prompt exists, in one conditional statement.
- **Learn on the user's own OpenRouter key can now run Sonnet.** Fine: it is their key. Grounding on Sonnet uses OpenRouter's web plugin; the existing retry-without-search covers a refusal.
- **Power's Normal and Max are a per-browser setting, else the suggested models** (`SettingsStore.tiers`, `TierStore`, apps/web). Each tier resolves to the saved choice while its route is usable and allows the model, else the tier-tagged model on the branch's own route (switching keeps who pays), on the default route, or on the first usable route listing one. The Normal | Max switch sits in the route bar and on the home page, and Compare runs the two resolved choices. On a branch whose provider lists no tiers (e.g. Anthropic on the user's key) the switch still shows, with neither segment on; picking one moves the branch to the route that has the tier, and the notice names that route ("Replies now on Max (Tangent credit)"), so a change of who pays is never silent.

## Hosted tier config (2026-10)

How the operator's hosted tiers ask their models is config, so a model or effort change is a config change. Brief: switching the hosted tiers' model (the model choice itself is decided apart).

- **A hosted tier is a model plus how it is asked: `{model, effort, reply cap, providerOrder}`.** Learn's Normal and Max (`SIMPLE_NORMAL_*`, `SIMPLE_MAX_*`: `_MODEL`, `_EFFORT`, `_REPLY_TOKENS`, `_PROVIDER_ORDER`) and the open pool (`POOL_MODEL`, `POOL_EFFORT`, `POOL_MAX_OUTPUT_TOKENS`, `POOL_PROVIDER_ORDER`), parsed in `config.ts` (`TierRequestConfig`). The settings travel on the tier's `ModelInfo` (`effort`, `maxOutputTokens`, `providerOrder`) in the built-in provider config (`withRequestConfig`, simple-mode.ts), so the provider applies them whoever pays (credit, or the learner's own key) and ChatService needs no tier logic. The pool's model carries the pool's settings, never a tier's, even on the same model id. Every default was the behaviour before: no effort sent, 16,384 out on a reasoning model (4,096 otherwise; the pool 8,192), OpenRouter's own routing. _Since_ Hosted models from the eval_, an empty var is the default model's evaluated setting while the tier runs it (`DEFAULT_TIER_REQUESTS`), and still the model's own on any other model._ A tier's reply cap can only lower the 16,384 per-call bound (it is the model's `maxOutputTokens`; larger values are clamped and logged). Power's Tangent credit drops the settings like it drops per-model limits (the user picks the model and reply length there). A `SIMPLE_PROVIDER` override ignores the vars, like the model vars; its models may set `effort` and `providerOrder` themselves (`PROVIDERS` too). `/api/providers` never lists them.
- **`ReasoningEffort` is `none | low | high`; there is no `max`.** At its top effort a model is far more verbose (about twice the median output) and, in Artificial Analysis' measurements of DeepSeek V4.1 Flash, almost never abstains when it doesn't know: the worst trade for a learning app. A `*_EFFORT` of `max` (or anything else) is refused and logged, falling back to no effort. `GenerateRequest.reasoning` (it was `'off'`, now `'none'`) overrides a model's effort per call: the pool's topic classifier sends `none`, summaries and titles `SIMPLE_FAST_EFFORT` (Learn's and the pool's; `ChatSettings.summaryEffort`). Sent only to OpenRouter (`reasoning: {enabled: false}` or `{effort}`, replacing an `extraBody.reasoning`); other endpoints may reject the field.
- **Thinking is dropped, not excluded.** The OpenAI-compatible parser reads only `delta.content` (Anthropic: `text_delta`), so streamed `reasoning` / `reasoning_details` are never shown or stored. `reasoning.exclude` is not sent: it changes nothing billed (thinking is billed either way, and usage still reports `reasoning_tokens`), and leaving it out keeps the request the same with or without an effort.
- **Reasoning is never sent back.** Nodes store only the answer text, and the upstream messages are `{role, content}` rendered from it, so no prior `reasoning` / `reasoning_details` can reach the model, the same way every turn (the cached prefix stays byte-identical).
- **Pinning a tier's providers keeps its prompt cache.** Each upstream keeps its own cache, and the cheapest-input providers of an open model often charge more for output, so a tier can name `providerOrder` (e.g. `deepseek`): sent as `provider: {order, allow_fallbacks: true}`, merged into the config's `extraBody.provider` (the pool's `max_price` stays; an operator's explicit `allow_fallbacks` wins). OpenRouter only.
- **MiniMax M3 is a config-only fallback.** `minimax/minimax-m3` has a placeholder price (0.30 / 1.20 / cache read 0.06 $/MTok, synced daily like the others), so a model var can name it, the pool included; it is no default. MiniMax recommends passing `reasoning_details` back between turns for its M2.x models (interleaved thinking). Tangent never does (above); check whether M3 carries the same recommendation before moving a tier to it, since following it would mean storing the thinking and resending it, which also changes the cached prefix.
- **A reply cut off at its output cap is not shown as an answer.** A `done` whose `stopReason` is `length` (OpenAI, OpenRouter) or `max_tokens` (Anthropic) ends the reply as an `error` node that keeps its text, with the fixed message `REPLY_CUT_OFF_ERROR` (stop-reason.ts); one cut off before any text (a reasoning model thought until the cap) gets `REPLY_THINKING_ONLY_ERROR`, and any reply without text `REPLY_EMPTY_ERROR`. No migration: status and message carry it, and every app tells it apart (`isCutOffReply`). Learn and power show "Cut off." with a **Continue** button on the branch's last message (it sends `CONTINUE_MESSAGE`; the partial reply is in the context, as error nodes with text always are); Canvas says "Cut off.". No title is generated, and no tangents are offered from it (its `<tangents>` block is lost anyway). There is no automatic retry with a larger cap: the thinking of the first try is billed regardless, a retry would bill it again, and the learner can continue instead. A cut-off Compare candidate fails rather than being held.
- **One log line per metered call, the charge still from actual usage.** The meter logs `{"event":"llm_call", usageId, funding, purpose, model, tier, effort, providerOrder, servedBy, maxOutputTokens, inputTokens, cacheReadTokens, cacheWriteTokens, outputTokens, reasoningTokens, costUsd, finishReason, truncated, error}` when a call it sent ends (`console.warn` when the cap cut it off), from the stream: OpenRouter's chunk `provider` (`billing.servedBy`) and `completion_tokens_details.reasoning_tokens` (`ProviderUsage.reasoningTokens`) are new. Cache hit rates and how often a tier's cap ends replies come from these lines (Workers Logs); `usage_events` keeps tokens and cost only, so no migration. Charges are unchanged: the reported cost (else the generation lookup, else tokens × price on the pool), never `max_tokens`, which only sizes the pool's hold.
- **The default prompt asks the tutor to flag uncertain specifics.** One stable line in `DEFAULT_SYSTEM_PROMPT`, after the accuracy rule: when it isn't confident about a specific fact (a name, date, number, quotation or citation), it says so instead of guessing. A tree keeps the prompt it was created with, so existing conversations (and their cached prefixes) are unchanged.
- **Prompt caching audit: nothing variable is sent, but three things moved the prefix.** No timestamps, ids or counters are in any prompt; the tree's prompt is stored per tree, and summaries are cached by content. (1) Fixed: a branch's anchor quote was a system section, so sibling branches with different excerpts diverged right after the tree prompt instead of after their shared ancestors; it is now an `<excerpt>` in the user turn where it occurs, everywhere (as the open pool already did), so siblings share the cached prefix up to their branch point. (2) Partly fixed: under the `auto` grounding policy the web search tool and its instructions are offered on some turns only. The instructions now follow the history (see Grounding), so they no longer move the prefix; the tool still does (it sits before the history in the providers' templates, and `tool_choice: "none"` does not keep it there, see Grounding), so a turn that gains or loses it misses the cache (`always-offer` would keep it stable, at the cost of more searches). (3) Fixed: past the input cap (`SIMPLE_MAX_INPUT_TOKENS`, the pool's 16,000), compaction moved the start of the history (and made a summary call) on every turn; it now compacts in whole steps down to about half the budget and keeps its boundary until the context grows another step (see Context). Truncation, the last resort, still shifts the history every turn it applies.
- **Power users can limit what a message sends.** Settings → Input limit (off, 16k/32k/64k/128k or a custom 1,000–2,000,000 tokens; `ui/input-limit-setting.ts`), saved in the browser and sent with each message (`SendMessageRequest.maxInputTokens`) like the reply length. On the user's own key nothing else bounded it but the model's window, so a long path could send hundreds of thousands of tokens per message. It only ever lowers the budget: ChatService `budgetFor` takes the least of the window less the reply, `ChatSettings.maxInputTokens` and the request (`RunGenerationOptions.maxInputTokens`). The Worker (`apps/worker/src/input-limit.ts`) drops it in Learn, and on Tangent credit caps it at `SIMPLE_MAX_INPUT_TOKENS`, with or without a setting: before, a model that doesn't reason could send the credit window less its 4,096-token reply (72,288 at the default cap), so "a credit call sends at most 60,000" holds now for every model. Reviews and Compare's candidates don't take the setting. _Since_ Wording and limits after the eval_: they do._
- **Over the limit: summarize (default) or drop, chosen per send.** `SendMessageRequest.inputOverflow` (`compact` | `truncate`, absent = `compact`). Truncation reuses the budget pass's last resort without touching `applyBudget`: `overflowBudget('truncate')` sets `compactionSummaryTokens` to infinity, so no prefix ever fits with a summary and the oldest non-system segments are dropped (never the target). Compacting already falls back to dropping when the summary fails (its segment is `failed` and left out) or the limit leaves no room for one (below about the system prompt + 1,024 for the summary + the last two messages). Power always has a summary model (`SUMMARY_PROVIDER_ID`, else the branch's own route), so both choices make sense there. Dropping changes the prompt prefix each time the conversation grows, like compacting does.
- **The Context panel plans like the next send.** `GET /api/branches/:id/context` takes `maxInputTokens`, `maxOutputTokens` and `inputOverflow` (`contextLimitsQuerySchema`), clamped as on a send; the panel passes the saved settings and reloads when they change. Before, it planned with the defaults, so its budget and compaction could differ from what a send did.
- **Token counts are shown in words, pages and dollars from one shared module.** `@tangent/shared` token-size.ts: ¾ of a word a token, 275 words a paperback page, SFWA's lengths (short story < 7,500 words, novelette < 17,500, novella < 40,000, novel beyond), two significant figures; the landing and pool pages' `roughWords` moved there. The cost uses the price table (`modelPrice`: OpenRouter list prices, only for models with a configured entry) through `GET /api/branches/:id/input-budget`, which also reports the window, the model's output limit and the server's cap; with no price the setting shows no cost rather than a guess. The price is the list price, without OpenRouter's fee or credit's markup. _Since_ Wording and limits after the eval_: on credit it is what credit charges, and the window of an OpenRouter model is its real one._

## Hosted models from the eval (2026-10)

A live eval (2026-10-08, through OpenRouter with the production prompt and message layout; 930 answers graded blind on accuracy, honesty, maths, teaching and flailing, plus 3 repeat runs of the maths and bait questions) set the hosted defaults. Code (`apps/worker/src/config.ts`) and `wrangler.jsonc` agree on them.

| Tier              | Model                          | Effort | Reply cap   | Provider order                 | Est. $ per 20-turn conversation    |
| ----------------- | ------------------------------ | ------ | ----------- | ------------------------------ | ---------------------------------- |
| Free pool         | `deepseek/deepseek-v4.1-flash` | `low`  | 8,192       | `streamlake/fp8,deepinfra/fp8` | about $0.022 ($0.015 on DeepInfra) |
| Learn Normal      | `deepseek/deepseek-v4.1-flash` | `high` | 16,384      | `streamlake/fp8,deepinfra/fp8` | about $0.027 ($0.021 on DeepInfra) |
| Learn Max         | `anthropic/claude-sonnet-5.5`  | unset  | 16,384      | unset                          | about $0.34                        |
| Summaries, titles | `deepseek/deepseek-v4.1-flash` | `low`  | (their own) | Normal's or the pool's listing |                                    |

- **The pool moves from V4 Flash to V4.1 Flash at `low`, for about the same cost.** Accuracy rose from 1.36 to 1.75–1.86 (of 2). Cut-off replies fell from 20% to none, empty replies from 11% to none, visible flailing (drafting notes, re-answering the previous turn) from 11% to 0–2%. No fabrications on the bait questions over 3 runs (V4 Flash made 2), 36/36 maths. Its longest reply in 76 calls was 4,401 tokens, so the 8,192 cap has headroom, and its slowest call (75 s) fits the pool's 120 s timeout.
- **Normal moves from V4 Pro to the same model at `high`.** V4.1 `high` beat V4 Pro on every quality measure (accuracy 1.86–1.95 vs 1.84, teaching 1.98 vs 1.68, honesty on the bait questions 2.00 vs 1.50: V4 Pro summarised a fictitious essay in all 3 runs) at about a third of the cost per conversation, and on one provider, so the prompt cache works (unpinned, V4 Pro went to 9 providers and got a 3% cache share).
- **Max stays on Sonnet 5.5.** The only configuration with perfect scores everywhere. It is about 15× Normal per conversation, which the usage note now says ("Max uses about 14× as much as Normal", from the list prices weighted 10:1; Compare "about 15× a Normal reply"). The copy reads the same at two digits; `MAX_USAGE_FACTOR_FALLBACK` is 14.
- **One model split by effort, plus a stronger Max.** Effort is a weak lever (`high` vs `low`: accuracy 1.86 → 1.95, about 1.5× the cost and 2× the latency; maths and bait were perfect at both), and no mid-priced model tested (MiniMax M3, V4 Pro, V4 Pro 0813) beat V4.1 `high`. The real step between tiers is Max's model. The pool therefore reads as "Normal" in the apps and on the public pages (it is Normal's model; the pricing page gives its shorter reply cap). _Since_ Wording and limits after the eval _below: "Normal's model with lighter thinking and shorter replies"._ `anthropic/claude-haiku-5.5` matched V4.1 `low` at the same cost and was the fastest (median 6 s); it is a candidate for the pool if latency draws complaints (it would need a `MODEL_PRICES` entry).
- **Summaries and titles move to V4.1 Flash at `low` too** (`SIMPLE_FAST_MODEL`, `SIMPLE_FAST_EFFORT`). V4 Flash cut off a fifth of its replies. `low` matters: background calls run on the model's listing in the provider config, which in Learn is Normal's (effort `high`). There is no `SIMPLE_FAST_PROVIDER_ORDER`; they share the listing's pinned providers (Normal's in Learn, the pool's on the pool), which for the default model is the same order.
- **StreamLake first, then DeepInfra, both fp8 and both caching.** StreamLake charges DeepSeek's own price ($0.15 / $0.60, cache read $0.003) and was 2–4× faster (V4.1 `high`: median 13 s vs 45 s; DeepInfra had 5 of 44 `high` calls over 120 s); DeepInfra is cheaper ($0.14 / $0.42 / $0.0042): put it first if spend matters more than latency. Quality was the same on both within noise. **Not `deepseek` (first-party):** OpenRouter filters that endpoint out for an account whose privacy setting denies paid-data training ("Paid model training violation"; every pinned call returned 404), and with `allow_fallbacks: true`, which production sends, the request then goes to any of about 28 providers, fp4 ones included, and loses the cache.
- **The request defaults belong to the default model.** An empty `*_EFFORT`, `SIMPLE_*_REPLY_TOKENS` or `*_PROVIDER_ORDER` is the table above only while the tier runs its default model (`withTierDefaults`, `DEFAULT_TIER_REQUESTS`; `backgroundEffort` for summaries). A tier moved to another model by config starts from that model's own defaults, since an effort or a provider slug tuned for V4.1 Flash says nothing about another model. The cost: on the default model, "no pinning" or "the model's own effort" can't be had by emptying the var (name another provider, or `none` / `low` / `high`).
- **V4.1 Flash's price is pinned in `MODEL_PRICES`, not left to the daily sync.** It is in `DEFAULT_MODEL_PRICES` at $0.15 / $0.60, cache read $0.003, 1,048,576 context, and `wrangler.jsonc` repeats it as an explicit `MODEL_PRICES` entry. OpenRouter's model-level list price for it, $0.0356 / $1.00, is no route's price (the cheapest input of one endpoint with a dearer output), and the sync would apply it (a drop of less than 10× is not held back). As the pool's `provider.max_price` that would admit only fp4 endpoints (OpenInference, Relace), which is plausibly what made V4 Flash flail on the pool: its placeholder was synced down to $0.03 / $1.28 the same way. An explicit entry wins over the synced price (`modelPrice`); the sync still records the list price in `model_prices` and its history, and logs `price_override_below_list` daily because the list's $1.00 output is above the entry's $0.60 (expected while the pinned providers charge $0.60). The entry also fixes the Max usage factor at 14. V4 Flash and V4 Pro keep their placeholder prices, so moving back is a config change.
- **Migration 0025 moves Learn branches on V4 Flash or V4 Pro to V4.1 Flash.** Edited in place (it had not been deployed): neither is a Learn model any more, so a send on such a branch would be a 400. Learn's old default-tier lessons keep the everyday tier. Only trees of `simple` accounts; power branches and history (`nodes.model`, usage rows, summaries) are untouched. Migration 0021 still moves `fake` branches to V4 Pro (its Normal model then); 0025 then moves Learn's on.
- **Limits of the eval.** 44 turns per configuration plus 3 runs of 16 maths and bait questions: differences of about 0.1 in mean accuracy among the strong configurations are within noise. Haiku and Sonnet ran only at their default effort. One grader. Prices change: the pool's `max_price` relies on the `MODEL_PRICES` entry.

## Wording and limits after the eval (2026-10)

Follow-ups to [Hosted models from the eval](#hosted-models-from-the-eval-2026-10): copy that had gone stale, and power's limits where sends already had them.

- **The privacy policy names the hosted models from the config, not "DeepSeek models".** It said Learn on credit uses "currently DeepSeek models", which stopped being true when Max became Claude Sonnet, and said nothing of the hosts V4.1 Flash is pinned to. `/privacy` now lists, under "Tangent credit and the open pool", each model Tangent pays for with what uses it (Learn's tiers by their labels, the open pool, summaries and titles), its maker (from the id's vendor prefix, `COMPANY_NAMES` in `http/hosted-ai.ts`, else the slug as is) and where OpenRouter sends it: the pinned hosts in order (`*_PROVIDER_ORDER`, the pool's resolved like a pool request, `poolRequest`) and whether it may fall back to others (an operator's explicit `allow_fallbacks: false` in `extraBody.provider` says "only"), else "a host OpenRouter chooses"; power on Tangent credit is "the model you choose". Uses are listed only while they are offered (`builtInAvailable`, `poolAvailable`), and a non-OpenRouter built-in endpoint is named by its host, with no hosting claims. The derivation works like the landing and pricing pages' (config in, wording out), so a model or host change by config needs no code change; the list is introduced as "at the moment", since such a change doesn't move `LEGAL_UPDATED` (bumped to 8 October 2026 for this change in substance). The policy makes no claim about any host's retention or training: that is a marked TODO for the owner in docs/LEGAL.md §5.
- **The pool is "Normal's model with lighter thinking and shorter replies", not "Normal".** It runs Normal's model at `low` against Normal's `high`, with an 8,192-token reply cap against 16,384, so plain "Normal" overstated it. `poolModelInfo` (pool/status.ts) compares the pool with the tier whose model it runs: its effort (`poolRequest`) against the tier listing's (`none` < `low` < `high`: `lighter` or `more`; one side unset: `other`, "a different thinking setting") and `POOL_MAX_OUTPUT_TOKENS` against a reply's cap on the tier (the listing's cap within the reasoning or plain default: `shorter` or `longer`). `GET /api/pool/status` carries the result on `model` (`PoolModelInfo.thinking`, `.replies`, absent when the same), and `poolModelText` (@tangent/shared pool.ts) words it for the landing page, `/pricing`, `/pool`, Learn's locked Normal/Max switch and both apps' pool cards. Asked the same way, it is plain "Normal" again; a model Learn doesn't list is still its own label ("Lite"). Copy that states the reply cap next to it (`/pool`, the pricing note) names only the thinking. No e2e: the pool is off in the e2e server, and the wording is a shared function the worker and app unit tests cover.
- **Compare's candidates and reviews take power's limits like a send.** `candidateRequestSchema` and `reviewRequestSchema` carry `maxOutputTokens`, `maxInputTokens` and `inputOverflow` (`generationLimitsShape`, shared with `sendMessageRequestSchema`), and the Worker clamps them with the same `generationLimits` before ChatService sees them (`prepareCandidate` / `prepareReview` take the clamped limits as their own argument and never read the request's): Learn drops them, the own key passes them through, Tangent credit caps the input at `SIMPLE_MAX_INPUT_TOKENS` with or without a setting. The funding that decides is the route that runs: a candidate's own route, and for a review the reviewer's (it is the one that reads the conversation), so a credit reviewer of an own-key branch now reads at most 60,000 tokens, where before it got the context as planned for the branch's model, up to that model's window. A candidate plans and streams exactly like a send with them; a review plans the reviewed conversation with the input limit and overflow choice on the branch's model (whose reply it is) and caps the review at the reply length, so the review prompt's own few lines come on top of the limit. Power's Compare dialog and review requests send the saved settings like sends (`generationLimits(settings)`); Learn sends none; the demo backend passes them like the Worker's own key.
- **OpenRouter models are budgeted on their real context windows (migration 0026, `model_windows`).** A model the provider config doesn't size (power's open OpenRouter list, on the user's key or on credit; Learn's tiers) got the `openai-compatible` kind's 128,000-token default: too small for most current models (V4.1 Flash and Sonnet 5.5 take about 1M), so long conversations compacted early, and too large for a few, whose calls then failed upstream. The daily price sync already fetched OpenRouter's `/api/v1/models`, which lists every model's `context_length` and `top_provider.max_completion_tokens`; it now also stores those for every listed model (priced or not) in `model_windows`, new and changed rows only, and a failure there is logged without undoing the prices (`syncModelWindows`, model-windows.ts). A new table, not more rows in `model_prices`: that table is the priced models' list prices with an append-only history, and unpriced or variable-price models (`"-1"`) have windows but no usable price. Neither KV (there is no binding) nor the Cache API (per colo, so the cron's write would reach one location) was a clean alternative.
- **Which window, and why the server budget changes too.** Every registry a request generates through (`registryFor`, `creditRegistryFor`) wraps its OpenRouter configs (`withModelWindows`): `LlmProvider.resolveCapabilities` (new, optional; the meter's and the pool's pinning wrappers pass it on) returns the config's capabilities with the model's real limits, looked up once per model per request: the price entry's window for a priced model (`modelPrice`: the configured window, lowered by the synced one), else its `model_windows` row, else nothing (the config stays). ChatService budgets with it (`budgetFor` is now async), so the Context panel, `GET /input-budget` and every send agree. A window the config names is only ever lowered to the real one, never raised: Tangent credit's (`SIMPLE_MAX_INPUT_TOKENS` + its 16,384 reply) and the pool's (its input plus output cap) bound their holds and input caps, so credit stays at 60,000 input at most and drops below it only for a model whose real window is smaller; a reported output limit only lowers the output limit. On the own key an unsized OpenRouter model now gets its real window: up to about 1M tokens a message without an input limit, where it was 128,000. That is what the model accepts and what the input limit is for (its hint shows the new default); it never exceeds the model's own window, which the old default could. Learn's budgets are unchanged in practice (its 60,000-token cap is far below the real windows). Other providers' model ids aren't OpenRouter's and pass through unchanged.
- **The input limit's cost is what the user pays.** On Tangent credit `GET /input-budget` prices the input at what credit charges, `chargeMicros(list, MARKUP_BPS, OPENROUTER_FEE_BPS)` (the billing helper the meter settles with, so list × (1 + fee) × (1 + markup)), and says so (`price.basis: 'credit'`); the hint reads "…on Tangent credit, which charges $0.1741 per million tokens of …'s input (OpenRouter's price with its fee and Tangent's markup)". On the own key it stays OpenRouter's list price (`basis: 'list'`), now only for an OpenRouter route (the table holds OpenRouter's prices), with "OpenRouter bills your key directly, and adds its fee when you buy OpenRouter credit", as the apps word own-key billing elsewhere.
