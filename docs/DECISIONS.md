# Decisions

The rules the code follows today, and why. One section per area. When a rule changes, edit it here in place: this page describes the present, and git keeps the past. The log this page replaced, with every superseded decision, is [archive/DECISIONS-2026-10.md](archive/DECISIONS-2026-10.md).

## Product and scope

- **Tangent is a branching chat for learning.** Any message can grow any number of branches, and each branch decides what the model sees (its context mode). Two apps share one Worker and one sign-in: the power app (`/`, `apps/web`) with every control, and Learn (`/learn/`, `apps/simple`), a tutor with nothing to configure. Canvas (`/canvas/`, `apps/canvas`) is a third, experimental view of the power conversations, as lanes on a surface.
- **Users read "tangent"; the code says "branch".** "Tangent" is the product's name and its verb, so every string a user reads (the apps, the landing page, shares and exports, the Flutter app, the user guide) calls a thread started from a message a **tangent** and the thread a conversation starts with the **main thread**, never a branch, fork, sub-thread or side question. Code, the API, the database, CSS classes and ids keep `branch`: renaming them would churn every layer and reach no user. `packages/web-shared/src/copy-rules.spec.ts` guards the templates. A tangent's default title starts `Tangent: ` (`DEFAULT_BRANCH_TITLE_PREFIX`), which every app strips when it shows the title, Flutter through a mirrored constant the parity test checks.
- **Self-hostable open source, run as one hosted deployment.** What a self-hoster needs stays configurable (URLs, legal names, providers, prices, payment provider); internal mechanics are constants ([Configuration](#configuration)). The name and logo are not licensed.
- **Pre-launch: no backward compatibility.** Production holds only the owner's data, so renames and removals ship without shims, fallbacks to old names, data migrations of old shapes, or upgrade tests. This ends at launch.
- **The money scope is fixed:** Tangent credit, the yearly membership, and the open pool. Nothing else is sold, and nothing is added to it without the owner. The impact feed, the pool's revenue share, credit included with the membership, pool purchases and the featured-conversations stub were removed in October 2026.

## Accounts and sign-in

- **Every user has one account, `u_<userId>`, in every app.** Power, Learn and Canvas are views of the same conversations. The `x-tangent-mode` header (absent means power), Learn's `x-tangent-payment` and its `x-tangent-own-key` (which own key, `openrouter` or `anthropic`; absent or unknown means OpenRouter, so a client that sends none, such as an older phone app, keeps working and the worst a bad value does is ask for an OpenRouter key) pick only how replies are generated and paid for (registry, profile, prompt, payer), never which conversations the caller sees. A conversation's stored settings may say anything; the server ignores, per request, what the mode doesn't allow, rather than rewriting them. Learn runs a branch whose provider or model it doesn't offer on its own provider and default model (`RouteResolver.runnable`), and honours the branch's context mode, which every mode can plan. `resolveAccount` (`apps/worker/src/auth/account.ts`) is the one place that decides the acting account; `AccountContext` is a union of the ways a request can act as it.
- **Credit is per user:** the account's id is its ledger id.
- **Ownership is checked in one place and answers 404.** Another account's tree, branch, node or share looks exactly like a missing one (`packages/core/src/services/ownership.ts`). The Worker resolves every id through it before it talks to a Durable Object, which trusts the account the Worker passes. A test generates the cross-user matrix from the route table, so a new id-taking route can't skip it.
- **Better Auth in the Worker, no passwords.** Google, GitHub, email and passkeys. Anyone with a verified email may sign up, up to `MAX_USERS` users when it is set: Turnstile on the magic-link form (the one endpoint that sends email) and its rate limits bound abuse. Google or GitHub signs a new user up as the email does; there is no email-first step, since the provider has verified the address and the pool asks for its own Turnstile pass. An OAuth identity links to an existing user only when the provider reports the email verified; trusting a provider wholesale would let an unverified address take over an account.
- **The sign-in email carries a link and a code; either signs in.** The code is for where the link can't reach: the phone app, or a computer the email isn't open on. It is 6 uniformly random digits from the CSPRNG (Better Auth's email-OTP plugin), lives 15 minutes like the link, works once, and dies after 3 wrong tries (the endpoint also allows 3 tries a minute per IP), so a guess has 3 chances in a million per email and every email takes a captcha. The only way to get a code is that captcha-gated email: the plugin's own endpoints that send codes, verify emails or reset passwords are disabled. It is stored encrypted with `BETTER_AUTH_SECRET`, not hashed: a hash of a 6-digit number is reversed by trying them all. Signing in by code does what the link does: creates the account, counts toward `MAX_USERS`, records the Turnstile pass while the pool is on. The one exception is `REVIEWER_SIGN_IN`, a secret email whose code is fixed and never emailed: app-store review needs credentials written down in advance, and the app signs in only by code. It goes through the same captcha, tries and single use, so guessing it means guessing a secret email too.
- **The phone app holds its session as a bearer token.** Better Auth's bearer plugin turns `Authorization: Bearer <token>` into the session on `/api/auth/*` and on our `/api/*`. Only the signed token counts (`requireSignature`), as only the signed cookie does, so the raw token in `get-session`'s body is no credential. The app's two sign-ins hand the signed token out in `set-auth-token`: the code, and a Google ID token (`POST /api/auth/sign-in/social {provider: 'google', idToken}`, Better Auth checking its signature and that its audience is `GOOGLE_CLIENT_ID`). No other response does, so the web apps' session stays in the HttpOnly cookie, out of reach of page scripts, which have neither the emailed code nor an ID token Google issued after the user picked an account. The ID token sign-in takes a Turnstile pass in `x-captcha-response`, as the sign-in email does, and records it while the pool is on: the app has no browser for the OAuth callback's interstitial. A bearer request carries no cookie, so CSRF doesn't apply to it: a page on another site can't make a browser add the header without CORS, which the Worker never grants. Remember me: an app sign-in that carries no `tangent-remember` cookie comes from a client without cookies, which keeps its token itself and has no browser session to end, so it gets the normal 30-day session; a browser's code sign-in carries its login page's choice. A link, an OAuth callback or a passkey without the cookie stays a one-day session, since it may be on a computer that never asked.
- **Turnstile for the phone app runs on `/app-captcha`.** Turnstile checks the hostname of the page that issued a token, so the app shows this Worker page in a web view: only the widget, with one script of its own (`/app-captcha.js`, allowed by `script-src 'self'`) that posts the token to the app's `TangentCaptcha` JavaScript channel. The app then requests the email as the web login page does.
- **The Worker fails closed.** Without `BETTER_AUTH_SECRET` every `/api/*` request is a 500. The dev bypass (`DEV_ALLOW_NO_AUTH=true`, exactly) works only while that secret is unset, and belongs in `.dev.vars`.
- **A sign-in returns to the page that asked for it.** A signed-out visit goes to the login page with `?returnTo=<path>` (the apps' `AuthService.requireUser`; the Worker's own pages through `signedInPage` in `apps/worker/src/auth/session.ts`), and every sign-in method carries the target in its callback URL: Better Auth keeps it in the OAuth state and in the magic link, so it survives the provider's round trip and a link opened in another browser, where a cookie wouldn't. Only a root-relative path on this origin is accepted (`safeReturnPath`, `packages/shared/src/auth.ts`, by Better Auth's own rules for callback URLs); anything else lands on the app's home, so the parameter is no open redirect. The admin app stays a 404 to anyone signed out rather than sending them to sign in, so it doesn't say it exists.
- **Every API write must be same-origin**, checked in one place for all routes, so a body-less destructive route doesn't rely on SameSite alone.
- **Admins are user ids in the `ADMIN_USER_IDS` secret.** To anyone else `/admin*` and `/api/admin/*` are 404. An id is not a credential: being an admin still takes signing in as that user.

## Context modes

- **Four modes, per branch:**
  - `path`: everything the parent saw at the branch point, plus the branch's messages. It is compositional, so a `path` branch under a summary branch doesn't re-expand what the summary dropped.
  - `summary`: a cached summary of the parent's context, focused by the quote.
  - `message`: only the message the branch forks from, as the parent saw it. The quote alone often lacks the answer around it; the whole path is more than the branch needs.
  - `independent`: only the quote or topic.
- **The tree's system prompt goes in every mode,** including `independent`: it is configuration, not conversation. **The anchor quote goes in every mode too,** as an `<excerpt>` in the user turn where it occurs (not in the system prompt), so sibling branches share the cached prompt prefix up to their branch point.
- **The mode decides what the tree's system prompt becomes, never the stored prompt.** A tree stores only a prompt its user typed (`trees.system_prompt`, set in power); a new or cleared one stores null, never a copy of a default, so a changed default reaches every tree that follows it. Power sends the tree's own prompt, else the default current at that reply: the account's saved prompt, else the built-in one (`systemPromptFor` in `packages/core/src/generation/context-resolver.ts`, the one place it is resolved). So power has no "no system prompt at all"; nobody asked for one. Learn always sends its current tutor prompt first, so its tangent buttons keep working, and never reads the tree's prompt; it adds the tree's learner instructions (`trees.learner_instructions`, edited from Learn's "Your instructions") after it only when the learner pays with their own key or credit. They are a column of their own because the tree's prompt is power's. The pool sends its locked prompt instead, and power ignores learner instructions. The account's saved default prompt is power's and Canvas's only.
- **`assembleContext` is pure and deterministic** (`packages/core/src/context/assemble.ts`). It plans the context; summaries are generated outside it and fed back, as many rounds as the nesting needs. Summaries are cached in D1 by anchor node and a hash of their transcript and focus, so a changed transcript means a new key and invalidation is implicit. A summary cut off at its output cap is used for the send that made it but never cached, so the next send summarizes again.
- **Over budget, compact before truncating.** The oldest part of the context becomes one cached summary, in whole steps of half the budget, so later turns find the same summary and send the same prefix (the prompt cache keeps working). Truncation is the last resort: when a summary can't be made or fails, the plan truncates instead and records it, and the send says so. Power users can choose to drop instead of summarize, per send.
- **Summaries run on the summary provider if the user can use it, else on the branch's own route** (`SUMMARY_PROVIDER_ID` without the user's key would otherwise silently lose summaries, titles and compaction). On Tangent credit they are billed like the reply, and a summary's prompt is clipped to the same input cap (`BUILT_IN_MAX_INPUT_TOKENS`), keeping its most recent part, so a long compaction prefix costs no more than a reply.
- **Tokens are estimated at 3.5 characters a token** plus the provider's reported usage. There is no tokenizer to ship. The open pool counts UTF-8 bytes instead, because its input limit must be a hard bound.

## Providers and models

- **Raw `fetch` and our own SSE parser, no vendor SDKs** (`packages/providers`). It runs on any Web runtime, aborts uniformly and handles OpenRouter's quirks explicitly. One HTTP layer serves the Anthropic and OpenAI-compatible providers, and `decorateProvider` is the one way to wrap a provider, so a new optional member can't be dropped by a wrapper that forgot it.
- **A provider id names an endpoint, never who pays.** The built-in provider is the endpoint `openrouter` (`OPENROUTER_PROVIDER_ID`) on the operator's keys; a user's own OpenRouter has the same id. Who pays is a separate fact ([Money](#money-credit-membership-and-the-open-pool)).
- **The built-in endpoint is a chain of hosted backends** (`apps/worker/src/hosted/`): OpenRouter, and Anthropic's own API when `BUILT_IN_BACKENDS` lists it and `BUILT_IN_ANTHROPIC_API_KEY` is set. Branches, usage rows, prices, windows, tiers and pages keep the model's _logical_ id, its OpenRouter catalog id; each backend maps it to its own (Anthropic: a constant list of the Claude models we use, so an unlisted model runs on OpenRouter instead of failing on an id Anthropic lacks). A call runs on the first listed backend that has its key and serves its model, and OpenRouter serves every model, so a model Anthropic lacks stays there. `usage_events.backend` and `backend_model` record where it was sent. A backend other than OpenRouter streams on a provider built from that backend's endpoint and key with the logical model's request settings; OpenRouter's routing (`providerOrder`, the pool's `max_price`) stays on OpenRouter's leg. Only metered calls run on backends: a user's own key runs on its own config and never reaches an operator key, and never falls back. A `BUILT_IN_PROVIDER` override replaces OpenRouter's endpoint and is the only backend.
- **A call falls back to the next backend only when one refuses it before any output** (`billing/meter.ts`): the leg ended in a rate limit, an overload, a server error or a failed connection that the upstream answered with an error status or never received (`ProviderError.upstream` `rejected` or `not_sent`), and yielded no event first. Then nothing was billed and the client has seen nothing of that leg, so the payer is charged once, for the backend that answered, and a started reply is never cut off. It runs the same logical model there, never another. A mid-stream error, a request the backend found wrong (bad request, context too long, key, payment) or an unknown failure is surfaced as it is, as is the last backend's error. The meter, not a provider wrapper, does it, because the row must follow the call (see [Tangent credit](#tangent-credit)). A fetch that fails before any response counts as `not_sent`, though in rare cases the request did reach the backend (the connection dropped after it went out) and that backend bills it: then the operator, not the user, pays for the lost attempt. That is accepted because the user is still charged once, for the backend that answered, and the alternative is to surface every transient network error to the user.
- **A backend that refuses a call goes last for a while** (`hosted/breaker.ts`): a rate limit or an overload, before or during the stream, puts it at the end of new chains for its `retry-after`, within 30 seconds and 5 minutes; a server error or a failed connection the backend refused or never got, for 30 seconds, as those say nothing of when to come back and a lone 500 should move the prompt cache off a backend only briefly. The breaker is per backend and model (the backend's id of it), as rate limits are per model: a Sonnet 429 leaves Haiku on Anthropic. A chain lists the closed backends first, then the open ones, each in the configured order; an open backend is moved, never dropped, so it stays a fallback if the others refuse too (the call's hold covers every leg). While it is open, calls start on the next backend and stay there instead of flapping back (the prompt cache is per backend); it only expires. The state lives in the isolate's memory, so it is best effort: another isolate learns from its own first refusal, which the fallback covers. The windows are constants, the same for every deployment.
- **Power's providers come from `PROVIDERS`** (default: Anthropic, OpenAI, OpenRouter), on the user's own keys only. The server keys those configs name serve only the local dev bypass. `openModels: true` makes a provider's models suggestions: any well-formed id is accepted, as OpenRouter adds models weekly.
- **What a provider can do is a capability flag, not its kind.** The test provider (`fake`) is for tests and offline development, never a default.
- **Request knobs live in the provider config** (a model's reasoning effort, OpenRouter's pinned providers and search engine), not in the shared request. An endpoint gets only the knobs its traits say it takes (`providerTraits`): effort goes to OpenRouter as `reasoning`, to Anthropic as `output_config.effort` and to OpenAI's own API as `reasoning_effort`, never to another OpenAI-compatible base URL (a local server may reject an unknown field); pinning and the search engine go to OpenRouter only.
- **Reasoning effort is `none | low | high`; there is no `max`.** At its top effort a model is far more verbose and almost never admits it doesn't know. Where an endpoint can't turn thinking off on every model (Anthropic, OpenAI), `none` is sent as the lowest effort they all accept, `low`. Thinking is never shown, stored or sent back, so the cached prefix stays byte-identical.
- **A reply cut off at its output cap is not shown as an answer.** It ends as an error node that keeps its text, with an `errorKind` (`cut_off`, `thinking_only`, `empty`, `cancelled`, …) stored in its own column. Apps decide by the kind, never by the English message; for nodes without a kind the message is mapped once (`errorKindOf`). Learn and power offer **Continue**; there is no automatic retry, which would pay for the thinking twice. Anthropic's `model_context_window_exceeded` and `pause_turn` (a paused server-tool turn, which nothing resumes) end a reply as cut off too; a `refusal`, or OpenRouter's `finish_reason: 'error'` without an error object, ends it as a `provider` error that keeps its text (`isLengthStop`, `failedStopError` in `@tangent/shared`).
- **Normal runs Claude Haiku 5.5, on credit and on the open pool alike.** Normal (Learn's model and power's Normal) is `anthropic/claude-haiku-5.5` at `high` effort, and summaries and titles run it at `low`: in the owner's use it answers better and loops less than DeepSeek V4.1 Flash, which matters more than price for a tutor that teaches facts. Haiku is pinned to Anthropic's own endpoint on OpenRouter, fallbacks allowed, so one provider keeps the prompt cache warm. Above 100K prompt tokens Anthropic charges five times as much for the whole request; the price table carries that tier (`longContext` of its entry), so a hold or token-priced charge whose input passes 100K uses those rates. Power's Max is `anthropic/claude-sonnet-5.5`. The open pool runs Normal too ([The open pool](#the-open-pool)). An empty tier var means these settings only while the tier runs its default model, and the DeepSeek V4 models stay priced so moving Normal to one is config alone.
- **Learn has one model, Normal; the Normal | Max tiers are power's.** Haiku is good enough for tutoring, and Max costs about 20× as much for a modest gain; a picker in Learn put that costly mode one tap away from a learner who can't judge the trade. Power keeps the switch, Compare and the Settings rows, on Tangent credit and in its own-key OpenRouter suggestions. A Learn branch stored on Max runs on Normal (`RouteResolver.runnable`), so old lessons need no migration. On the learner's own Anthropic key Learn runs power's Anthropic endpoint on a fixed pair instead: Sonnet for replies (the only model that config lists, so any other stored model runs as Sonnet) and Haiku for titles and summaries (`LEARN_ANTHROPIC_*_MODEL`, constants in `apps/worker/src/simple-mode.ts`). It is not configurable either; the dialog says so and points to power for other models. A learner with an Anthropic plan that includes API credit can then learn without OpenRouter.
- **Tiers are data:** `ModelInfo.tier` (`normal` | `max`), with every user-facing word for them in `@tangent/shared` `tiers.ts`. Branches store model ids, never labels. Learn's provider drops the `max` models of the built-in config; power's keeps them.
- **OpenRouter models are budgeted on their real windows,** synced daily from OpenRouter's model list into `model_windows`. A window the config names is only ever lowered to the real one, so credit's and the pool's bounds hold.
- **No provider names in the apps or the shared packages.** `scripts/check-provider-neutral.mjs` (in `pnpm lint`) keeps them out; ESLint keeps the Polar SDK inside its adapter.

## Web search (grounding)

- **OpenRouter's `openrouter:web_search` server tool (Anthropic's own `web_search` on an Anthropic backend), offered by a free gate, used at the model's discretion.** `decideGrounding` (`packages/core/src/grounding/policy.ts`) is a pure score: depth in the tree, a specific fact, recency, sources asked for. Searching every turn would multiply a lesson's cost about 15×; a classifier call adds latency and judges no better. At most one search per reply, on Exa, so the price is predictable. OpenRouter folds the fee into the reported cost, so billing needs nothing new. Anthropic's own `web_search` tool reports no cost, only the billed count (`usage.server_tool_use.web_search_requests`, 0 when it is absent, since an errored search is not billed), so a metered call on an `anthropic` config or backend adds $10 per 1,000 searches to its tokens at the list price, and holds the fee of every search the request allows (`unreportedSearchFeeMicros`, by the endpoint's kind; at the dearest backend a call may run on), as does a credit reply's reservation before its prompt exists while grounding is on. A call whose meter died is settled by the cron without the fee: the count comes with the stream's final usage. Other OpenAI-compatible endpoints (OpenAI's own API, a gateway, a local server) reject OpenRouter's tool, so a config there can't enable search: `PROVIDERS` refuses it.
- **Check sources forces a search and adds the check to the conversation** (in place on the last reply, else as a `path` branch), so later turns inherit the correction.
- **Citations are Markdown links in the reply.** The renderers show raw HTML as text (no sanitizer allowlist to keep the same on web and Flutter), so the default prompt and the search instructions ask for Markdown, never HTML. Follow-ups rely on them instead of searching again; summaries are told to keep them. `nodes.sources` is null when the reply didn't search and `[]` when it searched and cited nothing.
- **The instructions travel after the history,** on the reply's user turn, so the system prompt and the history are the same on every turn. The tool itself still comes and goes with the gate, which costs a cache miss past the tool block (`always-offer` avoids that at the cost of more searches).
- **`GROUNDING` is the operator's ceiling over both apps,** and the `GROUNDING_*` vars win over a provider's own options. `GROUNDING_ENGINE` and `GROUNDING_MAX_RESULTS` are options of OpenRouter's tool, so an Anthropic backend searches with its own engine. Power also has a per-branch setting; Learn ignores it. Automatic searches on credit stop for the day at `GROUNDING_AUTO_DAILY_CAP` per user.
- **Never on the open pool.** A pool hold is priced from tokens alone, so a search fee would be overage the operator pays.

## Money: credit, membership and the open pool

### Who pays

- **One `Payer` type: `own-key`, `credit` or `pool`.** Power stores it per branch (`branches.funding`: `own-key` or `credit`), so one tree can mix both. Learn decides it per request (the `x-tangent-payment` header plus the server's rules), so a Learn branch always stores `own-key`. In Learn the own key is the learner's OpenRouter key or, where the deployment configures power's Anthropic endpoint, their Anthropic key (`x-tangent-own-key`, remembered per browser like the payer); either needs the membership, and which one is no `Payer` of its own. Naming a provider never spends credit implicitly: a missing funding is `own-key`. `usage_events.funding` stores credit as `personal` (rows already written say so).
- **Learn's payer rule is one function, `learnPayer` in `@tangent/shared`,** used by the client and by the Worker's gate, and the reply's `start` event reports the payer the server actually used. The Flutter app can't import it, so `apps/flutter/lib/state/learn_payer.dart` copies it, with the same cases in its tests. In order: the own key if chosen; the pool if chosen and on; credit if sold; a saved own key; the pool if on; else the own key. A Learn send or context resolve on credit that can't cover its hold moves to the pool while the pool is on; reviews and Compare never do.
- **The default route of a new power tree** is `pickDefaultRoute` (`packages/shared/src/default-route.ts`), used by the Worker and both power apps: an own-key provider the user has a key for; else Tangent credit if it can pay; else OpenRouter on the user's own key. While own keys need a membership the user lacks and credit is sold, credit comes first. Credit is never a default that can't pay. Power's home page starts on the user's Normal instead when they chose one in Settings and its route can reply (`TierStore.starting`; on Tangent credit, a balance above zero), since the payer is then one they picked; never on a suggested Normal, which may be on another payer than the default.
- **A new power tangent starts on the open thread's route and web search,** the provider, payer and model the bar under the message box shows and that thread's search setting, wherever on the path its message is (`TreeStore.tangentRoute`): from the composer, a suggestion, Check sources or **Tangent from here**. The bar is where power says who pays, so a tangent from an earlier thread's message billed to that thread's route would charge a payer the user wasn't shown. Searches are billed to that payer too, so the setting comes from the same thread: the open thread's payer with an earlier thread's search setting would be a mix nobody chose. Check sources still forces its search. Whether a tangent can start is judged on that route too (`TreeStore.tangentLocked`), so a reply of a thread the membership locks, above a tangent that can reply, still offers its suggestions, and **Ask about this** puts its words on the message box. **Tangent from here** offers the default route instead where the open thread's can't reply in this browser; a read-only thread shows no bar, so its tangents keep their parent's route and web search. Learn's tangents keep the provider and model of the thread they come from, and its payer is per request.
- **A missing own key is a choice, not a wall.** A 401 `key_required` opens the keys dialog, saying the message wasn't sent and offering **Continue on Tangent credit**. Composers keep their text until the reply starts, so no refusal loses a message.

### Tangent credit

- **A dollar of credit is a dollar of usage at list price; the margin is a service fee on the purchase.** Buying N of credit costs N plus `serviceFeeCents` (20% + 50¢ by default), before tax, and credits exactly N; a call on credit sent to OpenRouter is charged the cost it reports, and one sent to Anthropic, which reports none, its tokens at the model's list price plus its searches' fee, rounded up to a micro-dollar. Buyers see what they pay and what they get before checkout, and nothing is taken from either afterwards. The fee's fixed part covers Polar's fixed fee, which otherwise makes small top-ups lose money; OpenRouter's and Polar's fees are the operator's costs, paid from the service fee.
- **A model has one price, whichever backend runs it:** the price of its logical id, with the usual precedence (`MODEL_PRICES` over OpenRouter's daily synced list price over the built-in table, a configured long-context tier kept). OpenRouter's list price for `anthropic/claude-…` is Anthropic's, so there is no Anthropic price table to drift from it. The pool's purchase fee (`OPENROUTER_FEE_BPS`, or the entry's `feeBps`) is OpenRouter's alone: a pool call sent to Anthropic is charged no fee, and its hold covers the dearest backend it may run on. The rates a call is charged at (both 0 on credit) are stored on its row.
- **The ledger is integer micro-USD, and the balance is derived:** grants minus settled charges, minus pending holds for "available". Grants are idempotent on the provider's object (`provider_ref` is unique); settles are conditional on `status = 'pending'`. There is no cached balance to get wrong.
- **Each call holds its worst case before it starts,** at its model's price (input bound and output cap), never below `USAGE_HOLD_MICROS` ($0.02). A reply is held before its prompt exists, at its whole input budget and reply cap: about $0.37 for a reply on power's Max at the defaults. The hold is inserted in the same statement that checks the balance and the in-flight limit (`USAGE_MAX_PENDING`, 6), so parallel sends can't overdraw. A model with no price can't run on credit.
- **A started reply is never cut off.** The reported cost can exceed the hold a little; the balance may go slightly negative and the next purchase absorbs it. The credit limit on `BUILT_IN_API_KEY` at OpenRouter is the backstop.
- **A call that falls back is one row, charged once,** for the backend that answered: the row is pointed at the next backend in one conditional statement (pending and dispatched; its hold and `dispatched_at` stay, as a request did go out) before that backend is called, and the facts the refused leg showed are forgotten, so its cost, tokens or generation id never reach the settlement. A reply reserved before its prompt existed is pointed at the backend it is sent on when it is repriced, as the breaker may have reordered its chain since. The switch is refused, and the error surfaced, when the row is no longer pending or its hold can't cover the next backend.
- **Lost costs are reconciled:** OpenRouter's generation endpoint with retries, then a 10-minute cron. Only a row sent to OpenRouter (or recorded before backends were) is looked up by its generation id; any other settles as a row without one. A call settles at $0 only when nothing can have been billed: never sent, or refused with a non-2xx status (`ProviderError.upstream`). A call that was sent but reported no cost and no generation id is charged the tokens it used at the list price, else its full hold, by the same rule as the pool (`billing/settle-policy.ts`). A call the user stopped (aborted, or stopped reading) without both token counts is charged its input, the count it reported or else the estimate its hold was sized with, at the input price, plus the reply text it streamed, estimated at 3.5 characters a token (rounded up, at most its output cap), at the output price: stopping a reply never costs its whole output cap. Thinking never streams as text, so the estimate leaves it out. A stopped call with a generation id is looked up instead. The pool follows the same rule with its input bound; its own timeout is no user stop and charges the hold. Every credit call is stamped `dispatched_at` right before it goes upstream, and its row keeps the input estimate its hold was sized with (`held_input_tokens`), so a row left pending 10 minutes without a generation id, whose meter died, settles by the same rule: released at $0 if never sent, else charged that estimate at the input price with no output, as a user stop (the meter dying is Tangent's failure, not the user's), else its hold. One with a generation id still unknown after 24 hours is `unresolved` at $0 and logged.
- **Refunds and disputes debit only the buyer's own ledger.** A refund debits the same share of the purchase's credit as of what was paid, once it succeeds, so a full refund takes back exactly the credit. Polar has no dispute webhooks, so the cron polls disputes. Dispute markers live in `billing_markers`, so `credit_grants` holds money only. A purchase's refunds and disputes together never take back more than it credited.

### The membership

- **The membership is required for generating on the user's own keys, and for nothing else** ($10 a year plus tax, one per user for both apps). Tangent earns from own keys through the membership and from credit through the service fee; a member who also uses credit pays both, each for what it covers. Credit is bought and spent without one; the pool never needs one.
- **It is off unless `ANNUAL_FEE_ENABLED` is on, a membership product is set and user keys can be stored** (`KEY_ENCRYPTION_SECRET`). With nothing to unlock, nothing requires or sells it. No credit comes with it.
- **Without a membership, nothing is locked away.** A power branch on an own key turns read-only: a notice where the composer was, offering renewal, **Open in Learn** (the same conversation, where Learn can reply on the pool or credit) and, while credit can pay, **Continue with Tangent credit**. Reading, export, backups, settings, delete and links stay. The server states the rule (`MeResponse.membershipNeededFor`), the clients don't copy it, and the server's gate stays the source of truth.
- **Waivers:** `auth_users.membership_waived`, set from the admin page or by the `MEMBERSHIP_WAIVER_CODE` code. A waived user is a member.

### The open pool

- **Free credit Tangent provides, for Learn users who can't pay,** funded by the operator with admin adjustments. Tangent earns money only from what it sells; nobody buys pool credit, and paying buys no more of it. No page may call it a donation or tax-deductible, or make a buyer the one who funds it (`FORBIDDEN_POOL_COPY`, checked by tests). Polar prohibits selling donations or community access.
- **Learn only, Normal's model, one locked prompt.** Power and Canvas never spend from it. The pool runs exactly what credit's Normal runs: the same model, effort, pinned providers and backend chain, and summaries and titles at the background effort. A learner who can't pay gets the same tutor, and it costs little: a pool reply on Haiku costs about $0.0008, so 10 a day stay far under the $0.10 per-user daily spend cap. The pool differs only in its limits (the caps below, its input, output and message caps) and, on OpenRouter's leg, `max_price` at the price table's price, so an over-priced route fails instead of costing the operator. Its reply cap is Normal's on credit, 16,384 tokens, and its ceiling hold (16,000 tokens in, 16,384 out) is about $0.017 at Haiku's prices. On the pool the server pins the model, the system prompt and the limits, whatever the tree says. No Compare, reviews or web search there.
- **The same daily caps for everyone:** replies and spend per user, per network (a daily-rotating hash of the IPv4 address or IPv6 /64, never the address) and for all users together. Per-minute limits too.
- **`PoolBank`, one Durable Object, serialises everything that can lower the pool's available balance,** with an explicit lock, because Durable Object input gates don't hold across D1 I/O. D1 stays the authority. Charges are clamped to their holds; the excess is operator-paid overage, and a breaker closes the pool when it exceeds $0.20 a day (a price below what calls really cost).
- **A reply reserves its ceiling hold before any node is written,** and that hold must fit under the per-user daily spend cap, or the pool reports itself off and logs `pool_misconfigured`.
- **A pool call's reservation is one row whose hold only shrinks,** grossed up by the dearest fee of the backends it may run on. It records the backend the call is sent on and charges that backend's fee; a fallback moves it to the next backend's fee only while that fee is within the one the hold was grossed up by, so a charge never needs more than the hold. The pool's call timeout runs from the first leg, so a fallback never outlives the reservation.
- **Access gates, each a 403 with its reason:** signed in, not suspended, a Turnstile pass on record, one pool identity per mailbox (a hash of the normalised email), and an optional minimum account age.
- **Pool limits fail closed.** The other rate limiters fail open so nobody is locked out of their own keys; the pool is the operator's money.

### Payments

- **Polar is the merchant of record,** behind a port (`apps/worker/src/billing/payments/port.ts`). Adapters translate Polar's objects into normalised events and never touch D1 or the ledger; `payments/apply.ts` decides. A new provider is an adapter, not a rewrite.
- **Membership state is ours,** from webhooks, upserted with a version guard so order and duplicates don't matter. No provider call per request.
- **A top-up's credit is the checkout's metadata,** `creditCents`, which only the server sets. The webhook never derives credit from the amount paid, so a change to the service fee between checkout and payment can't change what was bought.

## Privacy and retention

- **Users' API keys live only in the browser, sealed.** One AES-256-GCM cookie (`__Host-llmkey`, HttpOnly) holds every provider's key, sealed for the signed-in user (`uid`) with an expiry that slides: using the keys reseals the cookie once it is a day old, so keys lapse after 7 days unused, not 7 days after saving. Another user's cookie opens as no key, and sign-out clears it, so a shared browser never runs on the previous user's keys. The server stores nothing; the Durable Object opens the sealed value itself, in memory, per generation. The phone app has no cookie jar, so it keeps the sealed value in the platform keystore, as it does its bearer token, and sends it back as the cookie; never to `/api/auth/*`, where Better Auth refuses a write that carries cookies but no Origin. Rotating `KEY_ENCRYPTION_SECRET` revokes every key.
- **Nothing logs request headers or bodies.** They carry users' keys. Logs are structured events through one `logEvent` helper.
- **Providers get only the secrets their configs name,** never the app's other secrets.
- **Deleting is immediate and goes through the tree's Durable Object.** It aborts the tree's running generations (so nothing keeps billing for discarded text), deletes held Compare answers, then deletes the rows.
- **Account deletion keeps only what the open pool needs to stay fair, and nothing that leads to the person.** Usage rows lose their user id (amounts stay, so the pool's sums don't move); the network key goes once the day is over; the pool identity hash keeps its suspension and the day's usage for 90 days (`POOL_IDENTITY_RETENTION_DAYS`), so deleting and signing up again can't reset either. A daily sweep catches what a deploy missed. No reservation is written for a user who no longer exists.
- **Imports are bounded:** size and count limits in `treeBackupSchema`, and a rate limit per account.
- **The privacy policy follows the code.** It is rendered from the config (`apps/worker/src/http/legal.tsx`, `hosted-ai.ts`): which models Tangent pays for, their makers and pinned hosts. A change to what is collected or kept updates the policy and [LEGAL.md](LEGAL.md) in the same change.

## Sharing, export and links

- **The public viewer is a self-contained, server-rendered page, the same function as the HTML export.** It needs no session, has a strict hash-based CSP and lives on `/s/*` of the same hostname. Revocation is checked against D1 on every view, and cache keys include the version, so revoke and republish take effect at once. A share page keeps the conversation out of search and link previews: `noindex, nofollow` (meta tag, `X-Robots-Tag`, `robots.txt`), a generic title and description, and the conversation's title only in the page itself. It says above the conversation that the replies are AI-generated and that a user shared it, and labels messages "User" and "AI" (so does the export).
- **Every share is a snapshot,** projected when it is created or republished and never at view time, so what is public is what the owner published. A share with no stored snapshot is gone.
- **Private branches never enter a share or export payload** (the pure projection drops them and everything below them). JSON backups include everything.
- **Publishing has gates beyond `SHARING`** (`apps/worker/src/share/gate.ts`): a user whose sharing is suspended (`auth_users.sharing_suspended`) publishes nothing and their links are 404, as `canShare` decides for views too; an account publishes only once it is `SHARE_MIN_ACCOUNT_AGE_MS` old (admins exempt), so a throwaway account can't publish at once; and creates at most `SHARE_CREATES_PER_DAY` links in any 24 hours, counted from the audit log so deleting links doesn't reset it. Publishes the classifier refused count against the same limit, and once they alone reach it edits and republishes stop too, so retrying a flagged conversation can't hammer the classifier.
- **The audit log (`audit_events`) is append-only evidence** of what happened to shares, reports and holds: rows are only inserted (a test checks the sources), carry ids, versions and scores but never message content, and have no foreign keys, so deleting a share, a tree or an account can't remove them.
- **Legal holds preserve evidence outside the user's data** (`apps/worker/src/share/legal-hold.ts`): copies of a share, its snapshot, a backup of its conversation, the owner's user row and their sessions (never tokens), in `legal_hold_items`. No foreign keys reach them from shares, trees or users, so no revoke, delete or account deletion removes them; only an admin's release does, and not within a year of a recorded NCMEC or law-enforcement report. No API route returns the copies, so a stolen admin session can't script its way through them: the admin review page (`/admin/review/:shareId`, `apps/worker/src/http/review-page.ts`) renders a held snapshot once the share is gone, as a document with the viewer's CSP, and records each view; the operator reads the rest with `wrangler d1 execute`.
- **Every publish is screened when a classifier is configured** (`MODERATION_API_KEY`): creating a link, republishing it and giving it a new title send the text the page would show (the user's messages and the AI's replies alike, since the AI's words are where hosting liability is least settled, and every title) to OpenAI's moderation endpoint before anything is stored. The rules are pure and provider-neutral in `packages/core/src/moderation/` (pieces of 8,000 characters, 32 per call, at most 400,000 characters a publish, the thresholds); the adapter naming the provider is `apps/worker/src/share/moderation.ts`. `sexual/minors` at 0.1 or more refuses, places a legal hold on what was refused and alerts the operator by email (`apps/worker/src/alerts.ts`, ids only); the block thresholds (`illicit/violent` and `self-harm/instructions` and `hate/threatening` 0.5, `harassment/threatening` 0.6, `violence` 0.8) refuse; everything else publishes. Every refusal reads the same and never names a category, so the owner can't learn what to evade, and a CSAM flag isn't revealed. Screening fails closed: an error, a timeout or an answer missing a category refuses with "Sharing is temporarily unavailable." Each verdict's highest score per category goes to the audit log (`share_screened`), never the text, as the data to tune the thresholds with. Without the key nothing is screened and `SHARING=everyone` acts as `allowlist`, so strangers never publish unscreened.
- **Anyone can report a share, and some reports take it down before anyone looks** (`apps/worker/src/share/reports.ts`, the form at `/s/:token/report`, `apps/worker/src/http/report-page.tsx`). Liability follows knowledge plus inaction, and a link is unlisted and can be put back up, so taking it down is the cheap mistake. A report of CSAM, of violent or illegal content, or of copyright infringement (take down first, sort out later) sets `shares.takedown = pending_review` at once; defamation and harassment wait for two pending reports from different reporters, since one is often a dispute, and "other" only queues. A reporter is their user id when signed in, else the day's network key, so one person reporting twice counts once. CSAM and violent or illegal reports also place a legal hold and alert the operator. A taken-down link is gone like a revoked one, and its owner sees only "unavailable": no category and no review state, since telling them could tip off someone under investigation; they can delete it but not edit or republish it back up. The report form answers for a link that is down exactly as for an unknown one. Reports live in `share_reports`, with no foreign keys, and the audit log records each with its category only.
- **Admins decide reports from a queue, and strikes are derived from the decisions** (`apps/worker/src/share/review.ts`). **Remove** takes the link down for good (`takedown = removed`) and marks the share's undecided reports acted on; **Restore** puts it back up and rejects its reports, decided or not; **Reject** rejects one report and puts the link back up only if nothing still pending would have taken it down. A strike is a share of the owner's with a report acted on, counted from `share_reports` rather than stored, so a restore takes it back and several reports of one conversation are one strike. At two strikes the owner's sharing is suspended (`auth_users.sharing_suspended`, audited); lifting it is an admin's call, since a restore doesn't prove the other removal wrong. A removal with no report against it is no strike. The queue and the API return reports' words and metadata only; an admin reads the conversation on the review page.
- **One switch decides who shares, `SHARING`:** `off` (nobody, admins included, and every link is 404 at once), `allowlist` (admins and the users the operator allowed; the default) or `everyone` (only with a classifier, above). It is checked on every view, so changing it takes effect at once. A share's expiry changes only when the user picks one.
- **One backup format for both apps.** An import into Learn is adapted server-side (`adaptBackupForLearn`): Learn's provider and models, every branch `path`, every branch `own-key`; the tree's prompt is kept, since Learn never sends it. Nothing is charged by an import.
- **Links join two messages of one tree,** stored directed and shown on both ends, at most once per pair. They are owner data: in backups, not in shares or exports, and never sent to the model. They need no membership.

## Frontends and the shared engine

- **Angular 22, standalone, signals, zoneless, OnPush.** Workspace packages export TypeScript source, so there is no library build.
- **Shared logic lives once, in `packages/web-shared` or the `packages/*` below it, never copied between apps.** Three copies of the state engine drifted into bugs before October 2026. Today:
  - `ConversationStore` (`web-shared/src/conversation/`) is the engine every app's store extends: tree list, open tree, where the user is in it (path, crumbs, outline, focus on the path, opening a branch at its first message), live replies, the stream reducer, sends per branch, branch and link CRUD, resume. Apps supply hooks for their side effects.
  - `ConversationSidebar` (`web-shared/src/nav/`) is the conversation list with the open one's outline, in power, Learn and Canvas: for a large tree the outline is the quick way to any thread. The app's sidebar component provides itself as `SidebarHost` (its store, words, and what opening, renaming and deleting do) and projects its own head and foot; `SidebarState` holds the drawer, collapsed outline items and whether the user hid the sidebar on a wide screen, which each app remembers apart (a canvas wants the width more than a chat does). In Canvas, picking a lane in the outline selects it and the canvas moves to it, even when it is already the selected lane, since the click asks for exactly that.
  - `PowerConversationStore`, `PowerAccount`, the keys and Account dialogs, Import backup and the sidebar's account entries (`PowerSidebarFoot`) (`web-shared/src/power/`) are shared by power and Canvas. Shares and Billing are power's routes; Canvas's sidebar links them as power's pages.
  - The composer and its `ComposerController`, toasts, the dialog stack (`Overlays`), the shortcut dispatcher and the demo backend are shared by all three; the path keys (`pathKeys`), the shortcut table and the thread's scrolling (`ThreadScroll`, `JumpToEnd`) by power and Learn.
- **Each app holds its dialogs in one stack,** so Escape closes the top one and shortcuts never fire behind a modal. A dialog holding unsaved edits asks before Escape or a tap outside it discards them (the shared `Modal`'s `dirty`): both are easy to hit by accident, unlike Cancel and Close, which discard.
- **One meaning per icon** (`web-shared/src/ui/icon.ts`, whose keys name what they draw, never a meaning). The **gear** opens the app's Settings and nothing else. **Sliders** open the settings of one conversation or tangent (a lane in Canvas): power's Conversation and Tangent buttons and the route chip under its message box. A **caret** joined to a button is that button's action with options, named "… with options…": Tangent ↳ on power's message box, and Ask and Ask about this in Canvas, each opening Tangent from here. A **pencil** is text edited in place: a rename, a note, Learn's instructions, Canvas's Ask your own. A **left panel** (`panelLeft`) hides or shows the sidebar; the right one (`panel`) is power's context inspector. On a phone the header's Conversation and Tangent buttons show only their sliders, so the glyph alone must say they open one conversation's or tangent's settings, never the app's Settings, which the gear marks in the sidebar.
- **The HTTP API is one typed route table** (`packages/shared/src/api-routes.ts`): the apps' `ApiClient` calls it, the Worker validates with each entry's schemas, the demo backend must answer or refuse each route, and a test checks the Worker serves exactly those routes. Every JSON body is validated with zod (jitless, for the CSP).
- **Power's Settings live with the account, not in a browser.** Normal and Max, the default reviewer, the reply limit, the input limit and what happens over it are columns of `account_settings` beside the default system prompt, read and saved through `/api/settings`, so every device a user signs in on has the same ones. A model is three columns (provider, payer, model) written together, as branches store their route. The server validates each field with the bounds a send uses, and reads a stored value that no longer validates as its default, so a rule changed later never breaks the app. Power loads them with the account (`SettingsStore`); until they arrive a send or a review waits for them and Normal and Max resolve to nothing, so nothing goes out, or shows, on defaults the user replaced. The Settings dialog saves every change in one PATCH, all or none. Learn ignores these fields. What suits one screen (the text size, a dismissed banner) stays in the browser.
- **The demos run in the browser on the real `ChatService`** with in-memory repositories (`@tangent/core/memory`), the Worker's chat-settings builder and money math, and the same `GenerationHub` as the Durable Object. One repository contract suite runs against the memory and D1 repositories.
- **One Durable Object per tree (`TreeSession`) owns its generations:** streams outlive the tab, a reconnect replays, and sends are serialised per tree (any number of branches may generate at once; only a branch whose last reply is still streaming refuses a send). Deltas live in memory; the final text goes to D1 once.
- **The apps are served by the Worker's static assets,** with a strict CSP (`script-src 'self'`, and Trusted Types with Angular's policies, DOMPurify's and the diagram renderer's `default` policy, which takes HTML strings only while a diagram renders). The Worker sets the same CSP on the responses it renders itself (`/learn*`, `/`); a test keeps the copies identical. The Flutter app (`/app/`) has its own policy (`FLUTTER_APP_CSP`, `apps/worker/src/http/learn-app.ts`): `'wasm-unsafe-eval'` for CanvasKit, which is served from `/app/`, never Google's CDN; Turnstile on every page, because its sign-in is a route of the one document; Trusted Types with only Flutter's loader's policy, the app's Turnstile policy and dart2js's policy for loading the app's deferred parts (`dart.deferred-loading`, from `'self'`). It ships its fonts, because the CSP keeps the engine from fetching them from Google. Public pages (landing, pricing, pool, legal, verify) are server-rendered with `hono/jsx` in one layout: no script (the landing demo plays on CSS animations, with a checkbox and radio inputs for its controls; where the browser has scroll-triggered animations it starts once it is in view, and elsewhere on load, with no script fallback), escaping by default. They are built from the config, so they describe what this deployment sells, and their tests check facts (prices, limits, forbidden wording), not whole sentences.
- **The web apps offer the Android app in one quiet banner, on Android only, and once.** The app is Learn without the menus, which suits a phone, while the web keeps every control, so the web points to the app rather than replacing itself with it. Learn and power show a dismissible banner above the page (`AndroidAppBanner`, `web-shared/src/ui/android-app-banner.ts`) when the browser's user agent says Android, the deployment names an app (`ANDROID_APP_ID`, through `/api/me`), and this browser has loaded the app before: a newcomer meets the product before an install pitch. Following the link or closing it hides it in that browser for good (`localStorage`), and with storage blocked it never shows rather than showing on every load. A banner, not an interstitial or a dialog: search engines penalise app-install interstitials, and a dialog would block the learner's page. It takes the beta notice's place while it shows, so a phone's short screen holds one notice. Its link is the Play Store page with a `referrer` naming the placement, which Play Console's acquisition report counts. The landing page links the store page for every visitor, since a computer's Play page installs on the visitor's phone. Canvas and the demos don't offer it: Canvas is for wide screens, and the demos have their own banner.
- **Canvas is a view of the user's account, like power and Learn.** Its lineage view asks the real context planner (unresolved) rather than re-deriving it.

## Rendering replies

- **Mermaid diagrams, two engines, one contract.** The web apps draw with mermaid itself (`RenderDiagrams`, `packages/web-shared/src/ui/diagrams.ts`); the Flutter app with `mermaid_flutter` (native Dart, pinned to 0.3.x), loaded on demand as a deferred part of its web build. Both follow the same rules, with tests of the same names (`packages/render/test/markdown.test.ts` and the Flutter app's):
  - A fenced block, backticks or tildes, is a diagram when the first word of its info string is exactly `mermaid` (case-sensitive, as on GitHub), after entities are decoded and split on any whitespace. Inline code never is.
  - A diagram is drawn only once its message has stopped streaming; until then it is an ordinary code block. A half-written diagram rarely parses, and redrawing on every delta is wasted work.
  - A source over 20,000 characters (UTF-16 units of the fence's content, its last newline included), or one the engine can't parse or draw, shows as its code block under "This diagram could not be drawn."
  - A drawn diagram is an image labelled "Diagram: " and its node labels, comma-separated ("Diagram" without any); edge labels are left out. Its links are never followed. A wide one scrolls sideways. Its colours are mermaid's default or dark theme, by the app's brightness.
- **The tutor writes math in TeX,** `$…$` inline and `$$…$$` on lines of their own (`DEFAULT_SYSTEM_PROMPT`), the delimiters both renderers typeset. Some models do this unasked and others write `dy/dt = ky` as text unless told the app typesets it.
- **The tutor offers a diagram; it draws one when asked,** in one of the types both engines draw: flowchart, sequenceDiagram, classDiagram, stateDiagram-v2, erDiagram, pie, gantt, timeline, mindmap, with plain-text labels (`DEFAULT_SYSTEM_PROMPT`). Unprompted diagrams lengthen every structured answer for readers who didn't want one; a bare "Want a diagram?" says nothing about what it would show.
- **On the web, mermaid runs in the page, behind a gated `default` Trusted Types policy.** Angular's sanitizer strips SVG, so the drawing happens on the live DOM after it, as `TypesetMath` typesets math. Mermaid hands HTML strings to `innerHTML`, which the apps' Trusted Types refuse, so their CSP also names DOMPurify's policy and `default`. The `default` policy exists only once mermaid has loaded (on first use, with DOMPurify, so neither is in an initial bundle; `mermaid-render.ts`), throws for every string outside a running diagram render, as the CSP did before, and sanitizes with DOMPurify the strings inside one rather than passing them through. Mermaid runs at `securityLevel: 'strict'` on dagre, with `layout` a secure key so a diagram's `%%{init}%%` can't load ELK (1.4 MB); its SVG is sanitized again (the HTML profile too, for labels in `<foreignObject>`, and no `<img>`, so a label fetches nothing) and inserted as nodes, never as a string. Renders run one at a time, because `mermaid.initialize` is global. Not an iframe: a sandboxed frame needs a page of its own with its own CSP, and messages for its size, theme and text selection, for little gain over a policy that is closed except while a diagram draws.
- **Share links and exports show a diagram's source,** labelled; the viewer is one offline file with a hash-only CSP ([DEFERRED.md](DEFERRED.md#sharing)).

## Reply or tangent

- **Tangents are how you explore; Next is a plain reply. On the main thread, when in doubt, tangent.** The two mistakes don't cost the same there: a needless tangent is one click back, while a stray reply stays in the main thread, which the model reads on every later turn and every tangent's path context carries. So the apps put the choice where the learner sends, and the help explains tangents first and offers Next as ordinary chat, there if wanted, rather than as a step of the lesson. Power, Learn and Flutter show **Tangent ↳** and **Next ➜** side by side after a reply, always in that order; with a quote only Tangent shows, and with nothing to go on a tangent from, the plain Send. Enter sends with the filled one and Ctrl or Cmd+Enter with the other, and which is filled depends on where the learner is. On the main thread it is Tangent ↳, for the reason above. Inside a tangent it is Next ➜: going on is the natural step there, and a tangent by reflex costs a title call, another step in the path and, from depth 2, web search offered on nearly every turn (the depth score in `packages/core/src/grounding/policy.ts`, which takes that depth as chosen). So a reflexive Enter goes at most one level down, and every level below that is chosen. On a phone or tablet (no hover on the web; Android or iOS in Flutter, its browser build too) a plain Enter starts a new line and only the buttons send: a phone's keyboard has no Shift+Enter, and a tap on a labelled button says where the message goes. The rule is `composerPlan`'s (`packages/shared/src/composer-plan.ts`), which power and Learn web follow through one helper (`ComposerTarget` in `web-shared/src/conversation/composer-target.ts`) and Flutter mirrors (`lib/state/composer_plan.dart`): one rule, so a tangent from the message box means the same in every app. The shared `Composer` takes these as `actions`, each a button marked `data-action`, and fires the one marked `primary` on Enter. Power's **Tangent ↳** also has a caret (`options`; Ctrl or Cmd+Shift+Enter) that opens Tangent from here with the box's target, quote and text, for a tangent set up before it starts; the box lets the text go once the dialog has made the tangent, edited there or not, and a first message the server then refuses comes back to it, as any refused send does. Power has no **Ask your own** under each reply: a question of the user's own about a reply is the message box aimed at it (its Tangent ↳, `b`), so there is one draft rather than one per reply. Canvas lanes pass no actions and keep Send: each lane's box goes on in its own lane, and a card's **Ask your own** starts a new one.
- **The composer's tangent starts from the reply the learner is on** (`composerPlan` in `packages/shared/src/composer-plan.ts`, used by power and Learn web and mirrored in Flutter): the reply or words the box is aimed at (Ask about this, a reply's Tangent ↳, `b`), else the focused message of the open thread, a question standing for the reply that answers it, else the open thread's last reply. Someone who opened a tangent at its start is reading its first reply, and a tangent from its end would take turns they haven't read as context. Flutter has no focus to move (no `j` / `k`, no click to mark a message), so there the tangent's first message stands for it from when the tangent opens, at its start, until the learner sends or jumps to the end (`ChatController.plan`). Only the open thread's own messages are picked without aiming: an earlier thread's messages above are its context, and a tangent from one leaves the thread the learner is in, so it takes an explicit aim. The box names the reply ("↳ from “…”") when it isn't the last one or the end is out of view, deciding as the box opens and keeping that while it stays open, so the box doesn't change height under the learner's typing. Jumping to the end (`ThreadScroll.toEnd`; in Flutter, `End` or the jump to the end) lets the focus go, so a reply clicked long ago stops being where the tangent starts.
- **A tangent starts with its first message.** An empty tangent is a choice nobody made: the footer and the outline show it as a place the learner went, and a question asked again elsewhere is duplicated. So every way into a new tangent asks the question first, and the tangent is made when it is sent (`ConversationStore.startBranch` and `askFrom`; Flutter's `ChatController.startTangent`): "Ask about this" puts the words on the composer (`ComposerQuote`; in Learn and power a message's own Tangent ↳, or `b`, puts the whole message there, through `ComposerController.aim`, and in Flutter its Tangent ↳ through `ChatController.aim`; in Canvas, which has no single composer, a box over the canvas), and the tangent dialogs, the reviewer's included, require the starting message. Dropping the words or cancelling a dialog leaves nothing. The API still creates the branch and sends its first message in two calls, so a send the server then refuses (credit, the pool, a network failure) can leave an empty tangent; that is accepted rather than cleaned up, the text stays in the composer, and an existing empty tangent still opens and is started by its next message. A first message can't be compared (Compare runs on an existing branch).
- **A message is deleted with what follows it, and never edited.** Deleting one of the user's messages (`ChatService.deleteMessage`, `DELETE /api/nodes/:nodeId`) takes every later message of its thread and every tangent started from one of them, with everything below, through the tree's Durable Object like any delete. The later messages answer it and those tangents' context holds it, so nothing after it can stay; the confirmation says what goes, counted (`deleteMessageQuestion` in `web-shared/src/core/delete-branch.ts`, mirrored by Flutter's `lib/state/thread.dart`). There is no edit: resending an edited message would have to throw away the same things, and "delete it, then ask again" is easier to explain than an edit that also deletes. A reply can't be deleted alone, which would leave its message unanswered. A tangent's first message deletes the tangent, so no empty tangent is left.
- **Suggestions are tagged in-band.** Each line of a reply's `<tangents>` block starts `[deeper]` or `[tangent]` (`packages/shared/src/tangents.ts`, mirrored by `apps/flutter/lib/api/tangents.dart`). The tag lives in the text rather than in a provider's structured output, so it streams the same way through every provider over raw `fetch`, needs no provider-specific code, and stays in the stored message, where later turns see what was offered. `[dig deeper]`, `[continue]` and `[next]` read as deeper, because models paraphrase tags. An untagged line is a tangent: operator overrides of `LEARN_SYSTEM_PROMPT` and `POOL_SYSTEM_PROMPT`, saved custom prompts, power trees on the prompt they began with, and models that drop the tag all produce them, and an offer of unknown kind is shown as the one further out. At most 3 deeper and 6 tangent suggestions are kept, deduplicated by title, the first one winning.
- **Every suggestion opens a tangent; the kind only sorts them.** `[deeper]` is a question a reader of the reply would ask next, further into its topic; `[tangent]` is a related topic further out. Both are choices among several, so following one must leave the others open to try after it, from any reply, which a reply sent into the thread would not. Each opens a `path` tangent titled after it (`ConversationStore.followTangent`): a deeper question needs the conversation so far, and the kind doesn't set a lighter context mode, because the model's label is noisy and a mislabel would silently drop the context the answer builds on. The apps show them under **Dig deeper** and **Suggested tangents**; shares and exports list them as **Dig deeper** and **Tangents**, as the reply offered them.
- **A reply's tangents footer is sorted by where the user went** (`tangentFooter` in `packages/shared/src/tangents.ts`, mirrored by `apps/flutter/lib/api/tangents.dart`): **Your tangents** first, every tangent started from the reply, whether it followed a suggestion or was asked in the user's own words; then **Dig deeper** and **Suggested tangents**, the suggestions no tangent follows yet. A tangent follows a suggestion when it carries its title, and then shows once, as the user's. The footer is the only per-message mark of where the user left from: a followed suggestion left among the offers, or their own tangent shown small below them, would hide it. Once a reply has a tangent of the user's, both groups of suggestions fold behind one row (**4 suggested tangents**, or **3 more suggested** once one is followed): the user has read them, and the footer then changes only when the user starts a tangent (and moves to it) or deletes one, so nothing reflows above a reply streaming in, as a rule keyed to screen width or to the newest reply would. A reply whose tangent couldn't start folds them too (in power, one that would start on a route the membership locks; in Canvas, a locked lane's); Canvas's **Ask your own** stays outside the fold. The tangent on the open thread's path, and the one the user just came back from, are lit.
- **An opened tangent shows from its start, every time, with a quick way to its end; the main thread opens at its end.** Tangents are skippable: the footer and the outline always let the learner pass one by, so opening one says it is likely relevant, and landing at its end (on a phone above all) throws away the context it was chosen for. Reading down several tangents deep isn't the long-chat problem the main thread has: at each level the learner chose that tangent over the others, so what is on screen stays relevant. So power, Learn and Flutter open an existing tangent with its fork at the top of the view, and while the end is far below (more than half a view) a down arrow above the message box jumps there and follows a reply being written. The title, the open thread's own step in its path and `Home` go back to the start; `End` goes to the end (`Home` and `End` not while typing). The main thread opens at its end, where the lesson goes on, and so does a tangent just started, whose reply is followed as it streams. Going back up the path lands on the message the tangent left from on the web, and at the main thread's end in Flutter. Where to land is decided when the branch changes, so a follow of the old thread's end that was already asked for can't take the view to the new one's end. The web pages share this in `ThreadScroll` (`web-shared/src/conversation/thread-scroll.ts`); Flutter's is in `chat_page.dart`.
- **The help and walkthrough words live once, in `packages/shared/src/tangent-help.ts`:** the send buttons, the ways to a thread's two ends, the landing page's card (`apps/worker/src/http/tangent-help.tsx`), the Angular `TangentHelp` sheet (`web-shared/src/ui/tangent-help.ts`) and the coach marks read them. Flutter can't import them, so `apps/flutter/lib/ui/tangent_help_copy.dart` mirrors them and `packages/web-shared/src/tangent-help-parity.spec.ts` checks every string verbatim.
- **The "?" button is tangent help; the "?" key is keyboard shortcuts.** The visible **How tangents work** (the "?" in Learn's header and Flutter's app bars, the sidebar foot in power) opens the help, which links on to the shortcuts on the web. The key keeps the meaning keyboard users already know, and power's shortcuts button shows a keyboard, so only one "?" glyph means help. The landing card is always open, not a `<details>`, so the guidance is never hidden.
- **The first-run walkthrough runs once per account, in Learn web and Flutter.** Its flag is `account_settings.walkthrough_done_at`, read and set through `/api/settings` (`walkthroughDoneAt`; PATCH `{ walkthroughDone: true }`, a partial update), because the two apps share the account and Flutter keeps no client store. One pure reducer (`web-shared/src/walkthrough/walkthrough.ts`, mirrored by Flutter's `WalkthroughController`) shows each step once the screen has what it points at: Tangent ↳ after a reply on the main thread, the way back inside any tangent however it was entered, Next ➜ back on the main thread. Finishing or skipping sends the PATCH once; a replay from the help runs locally and leaves the flag alone. The demo keeps the flag in its session and starts each new one without it. Power and Canvas, for users past their first conversation, have no walkthrough.
- **Coach marks are our own and never block the page.** The learner moves on by using the control a mark points at, so there is no backdrop and no focus taken, and existing e2e and widget tests click straight through. On the web, `CoachMark` is a `popover="manual"` callout placed by `@floating-ui/dom` (MIT, maintained, computes positions only). driver.js writes its popover with `innerHTML`, which our Trusted Types CSP blocks, and widening the CSP isn't worth a tour; Shepherd and intro.js are AGPL; CSS anchor positioning alone isn't supported evenly yet. In Flutter, a ring and a callout sit in an `OverlayPortal` above the page, and only the callout takes taps: showcaseview and tutorial_coach_mark run a blocking, linear sequence on one route, while our steps follow the learner across routes on the controller's events.

## Deploy and migrations

- **GitHub Actions deploys, after CI passes** (`.github/workflows/ci.yml`, calling `deploy.yml`). On `master`, the sandbox (`--env sandbox`) deploys first and production second, after its reviewer approves, so every migration and deploy has run once on the sandbox's own database. Each deploy job runs in its own GitHub environment: build once from source with no secrets and no restored turbo cache, check that all five apps are in the assets, then `wrangler d1 migrations apply` and `wrangler deploy` with a config that has no `build` step (`scripts/deploy-config.mjs`), so the API token never meets the build toolchain and the upload is the build that was checked. One deploy at a time, never cancelled midway. Workers Builds is not used: it deployed whatever CI said and ran no migrations.
- **The `production` and `sandbox` environments allow only `master`.** Without that rule, a pull request that edits a workflow could run a job there and read the deploy secrets.
- **The sandbox is a second Worker, not a Workers Preview.** Cron Triggers run on production only, never on a Preview, so the billing backstops and dispute polling would go untested, and a shared preview database keeps every branch's migrations. `env.sandbox` restates every binding and var (wrangler inherits neither), and a test keeps it in step with production.
- **Migrations are applied before the code, so each must work with the code still running:** expand first (new tables, nullable or defaulted columns), contract in a later release. Re-running an old deploy redeploys old code onto the newest schema.
- **drizzle-kit writes every migration from `schema.ts`.** Never edit an applied migration, and never hand-write one. `pnpm lint` fails when `schema.ts` has a change no migration has (`scripts/check-migrations.mjs`). The history starts at `0000_baseline.sql` (the 27 earlier migrations were squashed before launch; production was converted once by hand, see [runbooks/d1-baseline.md](runbooks/d1-baseline.md)).
- **Durable Object class migrations in `wrangler.jsonc` are append-only too.**
- **Money tables are reached with raw SQL typed from `schema.ts`,** so a column rename is a type error in the ledger and the meter.

## Configuration

- **One module reads env: `apps/worker/src/config.ts`.** Every other module gets typed values from `appConfig(env)` and reads only bindings (a test checks). One parser per type; a malformed value fails every request with an error naming the var, so a typo never silently means the default.
- **A var exists only if a deployment has its own value for it.** Internal timings and limits that never change are constants (the pool's ledger id and reservation timings, the overage breaker, credit's minimum hold and in-flight limit). Money and abuse limits stay vars. `wrangler.jsonc` lists only this deployment's values (a test fails on one that restates its default).
- **One reference: [configuration.md](configuration.md),** kept in step with `CONFIG_VARS` by a test. Test-only vars (honoured only with `TEST_SEAMS`) are never documented.
- **Names say what they configure:** `BUILT_IN_*` for the built-in provider (Learn, power's credit and the pool), `LEARN_NORMAL_*` for Learn's model (also power's Normal), `POWER_MAX_MODEL` for power's Max, `BACKGROUND_*` for summaries and titles, `POOL_*` for the pool.

## Tooling

- **pnpm workspaces, with Turborepo running each package's tests, typecheck and build, not Nx;** TypeScript ~6.0 (Angular 22 needs `<6.1`); Vitest 4.1 everywhere; Node 24 (`.nvmrc`).
- **Turbo caches every per-package task** (`turbo.json`), locally in `.turbo/` and in CI through `actions/cache`. A task's hash covers its package's files and, through the `transit` task, its workspace dependencies'. A test that reads a file outside those names it in the task's `inputs`, and `scripts/check-turbo-inputs.mjs` (in `pnpm lint`) checks the globs reach it; a missing one is a stale cached pass.
- **Worker tests run in real workerd with real D1 and Durable Objects** (`@cloudflare/vitest-plugin`); suites that need neither run in plain Node. Every outbound call is mocked in one place. Coverage is reported, not enforced.
- **A live contract suite checks the providers and the money code against real endpoints, monthly** (`pnpm test:live`, [runbooks/live-contract-tests.md](runbooks/live-contract-tests.md)). Mocks only say what a provider did when they were written; the suite runs the real adapters, meters and settlement in workerd on production's provider and price vars, within a budget, and records what it saw as fixtures the offline tests replay. It never runs in `pnpm test` or CI, since it spends money and needs keys.
- **End-to-end tests sign in through the real magic link** (links printed to the server log, Turnstile's always-pass test keys) and set billing state through the fake payment provider's signed webhook, so production gains no test-only sign-in route. The sandbox runs Turnstile's always-pass test keys for the same reason: Cloudflare Access is its lock, and the config refuses a test secret with `POLAR_SERVER=production`.
- **Lint includes the type-aware promise rules, the provider-neutral check, the migration check, an import-cycle check** (`scripts/check-cycles.mjs`, runtime imports only) **and the turbo inputs check.**
